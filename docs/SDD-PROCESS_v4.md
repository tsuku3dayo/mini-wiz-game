# SDD-PROCESS v4：仕様書から作るアプリ開発の進め方（汎用版）

仕様書（Spec）を起点に、文書 → 実装 → テスト → リリースを、オーナー（人）と Claude Code で進めるための手順。
これまでのアプリ開発とふりかえりから、どのアプリにも流用できる形にまとめた。

- プロジェクトごとに変わるもの（ID の頭の文字・リポジトリ・技術など）は `<PREFIX>` のような `< >` で書いている。最初に 0 章で決め、プロジェクトの `CLAUDE.md` に書く。
- 技術に依存する注意（Web・PWA・Playwright・Windows など）は、8 章の「技術ごとの注意」に分けた。使わない技術の項目は読み飛ばしてよい。

| 版 | 日付 | 変えたこと |
| :--- | :--- | :--- |
| v4 | 2026-11-06 | ほかのアプリに流用できる汎用版として作った |

## 0. 新しいプロジェクトを始めるとき

### 0.1 先に決めること

| 決めること | 例 | 書く場所 |

## 1. 基本の決まり

| 決まり | 内容 |
| :--- | :--- |
| 指示で進む | Claude Code は、オーナーの指示なしに次の工程へ進まない |
| 承認はチャットで | 「承認します」「OK」で受ける。はっきりしない返事は確かめる |
| 承認の地点で止まる | 承認のある成果物を作ったら、承認を求めて止まる。承認の前に次の段階に進まない |
| PR ごとに区切る | 作業はブランチ → PR → CI が緑 → オーナーがマージ。既定のブランチ（`main`）に直接コミットしない |
| マージ = 公開 | main へのマージで公開されるなら、アプリが変わる PR は、そう伝えてからマージを頼む |
| マージ後の片付け | **`gh pr view <番号> --json state` が `MERGED` であることを確かめてから**、main を pull し、作業ブランチを手元と GitHub から消し、公開の実行と公開 URL を確かめる（オーナーの次の指示を、マージの合図と思い込まない。未マージの枝を消すと PR が閉じる） |
| 名前と機密の扱い | 了承をとっていない人の名前、ほかのプロジェクトの社内情報、個人の ID・機密を、公開リポジトリに書かない |
| 日本語で書く | Claude Code のメッセージ・コミットメッセージ・PR は、できる限り日本語（1.1） |
| 解説を付ける | エンジニアでないオーナーにも分かるように書く（1.1） |
| コマンドにリスク評価 | コマンドを動かす前にオーナーへ確認を求めるとき、コマンドの説明の頭に「【リスク：低／中／高（理由）】」を書く。低＝読むだけ（状態・ファイルを見る、テスト）、中＝手元のファイルを書き替える・作る（取り消せる。コミット・build など）、高＝GitHub に送る・消す・元に戻しにくい（push・PR の作成・ブランチの削除・ファイルの削除など）。1 つのコマンドに複数あれば、いちばん高いものを書く |

### 1.1 言葉と解説

**日本語で書くもの**
- Claude Code のメッセージ
- コミットメッセージ。1 行目に何をしたかを短く書き、必要なら 1 行空けて理由を書く（1 コミット 1 目的）
- PR の題名・本文・コメント
- 成果物・ふりかえり・変更の依頼

**英数字のままにするもの**：ブランチ名・ID・ファイル名・コマンド。日本語にすると、道具によって文字化けしたり、入力しにくくなったりする。

**解説の付け方**
- 専門の言葉（ブランチ・PR・マージ・CI など）は、はじめて出たところで短く言い換える（例：「PR（変更を本流に入れてよいか確かめてもらう申請）」）。付録 B の言葉の表を使ってよい。
- 何をしたかだけでなく、なぜそうしたか・オーナーにとって何が変わるか・次に何をしてほしいかを書く。
- コマンドやファイル名をただ並べない。必要なものだけ示し、意味を添える。
- 承認を求めるときは、決めてほしいことを選択肢と推奨で示し、選んだあとに何が起きるかを添える。

**文字化けを防ぐ**（Windows の PowerShell 5.1 など）：日本語のコミットメッセージ・PR の本文は、BOM なしの UTF-8 のファイルに書いて渡す（`git commit -F <ファイル>`、`gh pr create --body-file <ファイル>`）。GitHub でマージしたときに自動で付く題名（「Merge pull request #n …」）は英語になる。日本語にしたいときは、マージの画面で書き換えるか、リポジトリの設定で PR の題名を使うようにする。

## 2. 開発工程のフロー

### 2.1 全体の流れ

`［ ］` はオーナーが出す指示、`◆` はオーナーの承認。

```
          仕様書（docs/specification-ja.md）
                     │
                     ▼  ［仕様書をもとに project-brief を作ってください］
┌──────────────────────────────────────┐
│ 00 プロジェクト概要                  │  project-brief
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［01 システム構成を作ってください］
┌──────────────────────────────────────┐
│ 01 システム構成                      │  system-architecture
│                                      │  technology-stack
│                                      │  architecture-decision
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［02 要件・ユーザーストーリーを作ってください］
┌──────────────────────────────────────┐
│ 02 要件・ユーザーストーリー          │  epic（優先順位 = 07 の WS の順）
│                                      │  user-story
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［03 画面設計を作ってください］
┌──────────────────────────────────────┐
│ 03 画面設計                          │  gui-design
│                                      │  試作（公開 URL に置き、実機で触る）
└──────────────────────────────────────┘
                     │  ◆ 承認（試作を実機で触ってから）
                     ▼  ［実行してください］
┌──────────────────────────────────────┐
│ 04 詳細設計                          │  technical-design
└──────────────────────────────────────┘
            ┌────────┴────────┐
            ▼                 ▼
┌───────────────────┐ ┌───────────────────┐
│ 05 テスト         │ │ 06 作業計画       │
│  test-strategy    │ │  workstream       │
│  test-case        │ │  impl-task        │
└───────────────────┘ └───────────────────┘
            └────────┬────────┘
                     │  ※ 04〜06 は承認なし。段階ごとに「進めてよいか」→ PR
                     ▼  ［WS-<番号> を始めてください］
┌──────────────────────────────────────┐
│ 07 実装・自動テスト                  │◀─────┐
│   TASK ごとに：                      │      │
│   ブランチ → テスト → 実装 → PR      │      │
│   → CI が緑 → マージ（= 公開）       │      │
│   → attested-computation（draft）    │      │ 次の WS
└──────────────────────────────────────┘      │
                     │                        │
                     ▼                        │
┌──────────────────────────────────────┐      │
│ 手動テスト（WS の終わり、実機）      │      │
│   attested-computation（review）     │      │
│   ふりかえり（ws-<番号>.md）         │      │
└──────────────────────────────────────┘      │
                     │  ◆ 承認 ───────────────┘
                     │
                     ▼  最後の WS が終わったら ［リリースしてください（版）］
┌──────────────────────────────────────┐
│ リリース                             │  版の確定・README
│   マージ（= 公開）→ 全体の手動テスト │  attested-computation
│                                      │  ふりかえり（release.md）
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［再現開発仕様書を最新にしてください］
┌──────────────────────────────────────┐
│ 完了                                 │  再現開発仕様書
│                                      │  ふりかえりのまとめ（summary.md）
└──────────────────────────────────────┘
```

### 2.2 途中で仕様を変えるとき（変更の依頼。いつでも）

```
［変更のメモ（何を・なぜ・画面のイメージ）］
                     │
                     ▼
┌──────────────────────────────────────┐
│ 変更の依頼を書く                     │  docs/requests/<日付>-spec-<版>-<内容>.md
│   内容・影響の一覧                   │  （直す成果物・テスト・コード）
└──────────────────────────────────────┘
                     │  ◆ 進めるか・見送るか・範囲を絞るか
                     ▼
┌──────────────────────────────────────┐
│ 仕様書の版を上げる                   │
│ 影響する承認済みの成果物を review に │  PB・ADR・US・GUI など
└──────────────────────────────────────┘
                     │  ◆ 承認 → PR
                     ▼
┌──────────────────────────────────────┐
│ 設計・テスト・計画を直す             │  TD・TC・TST
│ 修正用の WS・TASK を足す             │  WS・TASK → PR
└──────────────────────────────────────┘
                     │
                     ▼
       07 実装 → 手動テスト → ◆ 承認（2.1 と同じ）
                     │
                     ▼
       影響の一覧の「結果」をすべて埋めて「完了」
       （完了のあとに変えたときは、再現開発仕様書の第 1 部も直す）
```

## 3. 成果物

### 3.1 種類と置き場所

ID は `<PREFIX>-<種類>-<4 桁の通し番号>`（例：`<PREFIX>-US-0001`）、ファイル名は `<ID>-<種類名>-ja.md`（例：`<PREFIX>-US-0001-user-story-ja.md`）。通し番号は種類ごとに 0001 から振り、欠番は使い直さない。

| 工程 | 種類名 | ID の種類 | 置き場所 | 承認 |
| :--- | :--- | :--- | :--- | :--- |
| 00 | project-brief | PB | `docs/00_brief/` | あり |
| 01 | system-architecture / technology-stack / architecture-decision | SA / TS / ADR | `docs/01_architecture/` | あり |
| 02 | epic / user-story | EP / US | `docs/02_requirements/` | あり |
| 03 | gui-design | GUI | `docs/03_gui/` | あり |
| 04 | technical-design | TD | `docs/04_design/` | なし |
| 05 | test-strategy / test-case | TST / TC | `docs/05_test/` | なし |
| 06 | workstream / implementation-task | WS / TASK | `docs/06_plan/` | なし |
| 07 | attested-computation（実施記録） | AC | `docs/07_attested/` | あり |

ID のない文書：仕様書 `docs/specification-ja.md`、変更の依頼 `docs/requests/`、ふりかえり `docs/retrospectives/`、再現開発仕様書 `docs/reproduction-specification.md`。

### 3.2 frontmatter

```yaml
---
id: <PREFIX>-US-0001
type: User Story            # 種類名を英語の見出し形で（project-brief → Project Brief）
title: タイトル画面から始める # 日本語の短い名前
status: review              # draft（作成中）→ review（承認待ち）→ stable（承認済み・確定）
version: 1.0
updated: 2026-01-01
sources:                    # 根拠にした成果物の ID と版・資料
  - <PREFIX>-EP-0001（v1.0）
  - docs/specification-ja.md (v1.0) §7
verified: null              # 承認されたら { by: "<オーナーの GitHub ID>", at: "<日時（ISO 8601、+09:00）>" }
---
```

- 承認を求めるときは `status: review` にする。オーナーがチャットで承認したら `status: stable` にし、`verified` に承認者と承認日時を書く。
- 承認のない段階（04・05・06）の成果物は、書き終えたら `status: stable`・`verified: null` にする。

### 3.3 番号の決まり

- test-case の番号は user-story と同じ。AC の番号は TASK と同じ（TASK-0004 の記録は AC-0004）。
- TASK のない記録（リリース・完了）に AC の番号を使ったら、次の TASK はその番号を飛ばし、TASK と AC の番号をそろえる。
- 確認 ID は `<PREFIX>-TC-<4 桁>-<2 桁>`。自動テストは名前の先頭に確認 ID を書く（例：`TC-0002-03`）。
- 非機能の test-case の番号の付け方は、05 の最初に決める（あとから足すストーリーとずれないように）。

### 3.4 版の上げ方

| 場合 | すること |
| :--- | :--- |
| 中身が変わる | 版を 0.1 上げる。承認のある種類は `status: review`・`verified: null` に戻し、再承認 |
| 上流の版が上がったが、中身は変わらない | sources の版の表記だけ直す（承認済みのまま。版・status・verified はそのまま。直したことを PR に書く） |

版の上げと、全成果物の sources の表記そろえは、スクリプト（`scripts/`）で行う。最初から用意しておく。

### 3.5 attested-computation（AC：実施記録）

- implementation-task（何をやるか）と test-case（どう確かめるか）に対する、「実際にやって確かめた結果」。
- 本文：実施概要（タスク・実施者・環境）／確認結果（テストケースの手順ごと）／**確認できなかったこと**（正直に書く）／後片付け／完了定義のチェックリスト。
- `sources` に対応する TASK と TC の ID を書く。
- `draft` で作って自動テストの結果を書き、**TASK の PR に一緒に入れる**。WS の終わりに手動テストの結果を足して `review` にし、オーナーの承認を受ける。

## 4. 工程ごとの進め方

### 4.1 承認のある文書（00〜03）

- [ ] main を最新にし、`docs/<工程>-<内容>` を切る（例：`docs/03-gui-design`）
- [ ] 入力の成果物を読み、決めてほしいことがあれば、選択肢と推奨を示して先に聞く
- [ ] 成果物を `status: review` で書く
- [ ] 整合性チェック（7 章）を確かめ、check:docs を通す
- [ ] 03 では、試作を公開 URL に置き、実機で触ってもらう（下の「03 の試作」）
- [ ] コミットし、要点と決めてほしいことを解説つきで短く示して承認を求め、止まる（push はまだしない）
- [ ] 承認を受けたら `status: stable`・`verified` を書いてコミット
- [ ] push して PR（本文に成果物の ID・版・承認日時）→ CI が緑 → マージを頼む
- [ ] マージされたら片付け（1 章）

| 工程 | 開始の指示（渡すもの） |
| :--- | :--- |
| 00 | 「仕様書をもとに project-brief を作ってください」（仕様書、対象の端末、公開先） |
| 01 | 「01 システム構成を作ってください」（流用するもの、使いたい／使いたくない技術） |
| 02 | 「02 要件・ユーザーストーリーを作ってください」（優先順位の付け方） |
| 03 | 「03 画面設計を作ってください」（参考の画面、基準の端末） |

**03 の試作**：画面の大きさ・配置と主な操作だけの試作を `prototype/` に置き、公開 URL で実機で触ってもらう。本物とは**名前・アイコンを変える**（取り違え防止）。スマートフォンが対象なら、確かめること：指で大事なものが隠れない／押す部品は 44 px 以上／一番小さい端末で 1 画面に収まる／キーボード・ノッチ・ホームバー／ホーム画面で名前が切れない／文字が読める。

### 4.2 承認のない文書（04〜06）

- [ ] 始める前に「進めてよいか」を確かめ、「実行してください」を受けてから `docs/<工程>-<内容>` を切る
- [ ] 成果物を書き、整合性チェック（7 章）を確かめ、check:docs を通す
- [ ] `status: stable`・`verified: null` でコミット → PR → CI が緑 → マージを頼む

### 4.3 07 実装（TASK ごと）

開始：「WS-<番号> を始めてください」

- [ ] main を最新にし、TASK の文書に書いた名前でブランチを切る（`feat/<TASK 番号>-<内容>`。直しは `fix/…`、道具は `chore/…`）
- [ ] TASK の「やること」と対象の確認 ID を読む。WS の最初の TASK では、WS の全 TASK について、「やること」に書いた道具（自動で操作するテスト用の仕組みなど）が使う機能も、その TASK の時点でそろうかを確かめる（確認 ID の点検だけでは漏れる）
- [ ] テスト（名前の先頭に確認 ID）を書く → 実装する
- [ ] 手元で検査（lint・単体・build・配布物の検査・check:docs。例：`npm run verify`）と E2E（画面を実際に動かす自動テスト）を通す
- [ ] check:docs の「テストのコードにある確認 ID の数」が、その TASK の自動の確認 ID の数だけ増えたかを確かめる（確認 ID が数えられていなくても、注意の数だけでは気づけない）
- [ ] 画面の変更は、PC と一番小さい対象端末の幅でスクリーンショットを見る
- [ ] 設計と違う作りにしたら TD・GUI を直す（承認済みのものは再承認）
- [ ] AC（draft）に自動テストの結果を書き、同じ PR に入れる
- [ ] 公開版に、途中までしか使えない場面（まだ作っていない画面へ進むなど）が残るときは、PR とオーナーへの報告に、その場面と抜け方を書く
- [ ] PR → CI が緑 → マージを頼む（マージ = 公開）

### 4.4 WS の終わり（手動テスト）

**マージ（公開）の前に**
- [ ] 版の切り替えを確かめる WS では、最後の TASK をマージする**前に**、実機で今の版を一度開いてもらう
- [ ] 実機の確認の手順と「見ることの一覧」は、マージ（公開）の**前に**渡す。公開のあとでは、手順の前半（データを作る・操作を進めるなど）をやり直せないことがある。アプリの更新が「開き直したときに届く」作りなら、そのことも先に伝える
- [ ] 実機ではすぐに行けない場面（めったに起きない出来事・終盤の場面など）は、テスト用の入口（例：`?debug=1` と開発者ツールのコンソール）に貼るだけで作れるコードを用意し、**手元で自動テストの道具で動かしてから**手順と一緒に渡す

**案内の書き方**
- [ ] 確認ごとに「OK／NG／見ていない」を書き込める返事のひな形を付ける（端末が 2 つなら端末ごとに）。まとめた返事でも、AC に確認ごとの結果を残せるようにするため
- [ ] **最初に「どのアプリで確かめるか」**（公開 URL か、ホーム画面に入れた本物か、試作か）を確かめてもらう
- [ ] 実機ではすぐに行けない場面を案内の中で先に挙げ、探さなくてよいと伝える。その場面は E2E とスクリーンショットで確かめたと AC の「確認できなかったこと」に書く
- [ ] 端末の機能（読み上げ・ホーム画面への追加など）を使うときは、オンにする手順と元に戻す方法を付ける。端末にない道具（例：iPhone の Safari には開発者ツールのコンソールがない）が要る手順は、PC で行うか、案内から外して AC の「確認できなかったこと」に書く
- [ ] 確認を、テストケースの手順の一部にしぼって頼むときは、しぼった理由と「今回は見ない手順」を案内に書き、AC の「確認できなかったこと」にも書く

**結果を受けたあと**
- [ ] WS の TASK がすべてマージ・公開されたことを確かめる
- [ ] 結果（OK、または NG と様子・スクリーンショット）を受け取る。結果なしの「承認」は、結果を先に確かめる
- [ ] `docs/ws-<番号>-ac` で、AC に手動の結果と「確認できなかったこと」（持っていない端末など）を書き `review` に
- [ ] 同じブランチで、ふりかえりの案（9 章）を書いて見てもらう
- [ ] 承認を受けたら `stable`・`verified` → ふりかえりの T をこの文書に反映 → PR → マージを頼む
- [ ] 次の WS は、指示を受けてから始める

実機で原因が分からないときは、推測で直すのは 1 回まで。次は、画面に状態を出す一時的な診断を入れ、記録を見て決める（WS を閉じる前に消す）。

### 4.5 リリース

開始：「リリースしてください」（バージョン番号）

- [ ] 版の番号（例：`package.json` の version）を決め、画面の版の表示を確かめる
- [ ] 仕様書の受け入れ基準のすべてに、確認 ID と結果があることを一覧で確かめる
- [ ] check:docs を厳しいモード（未実装・未記録も 0）で通す
- [ ] README（使い方・権利やクレジットの表記）がそろっているか確かめる
- [ ] 「マージ = 公開」と伝え、公開前に入れたいものがないか聞いてから、マージを頼む
- [ ] 公開後に、全体の手動テストを案内する → AC を review → 承認 → PR
- [ ] AC と同じ PR に、リリースのふりかえり `release.md` を入れる

リリースの AC には TASK がないので、最後の TASK の次の番号にし、その理由を AC に書く（3.3）。

リリースで画面や仕様に足りないものが見つかったら、変更の依頼（6 章）として修正用の WS・TASK を足し、その TASK の PR をリリースの PR にする。

### 4.6 完了

開始：「再現開発仕様書を最新にしてください」

- [ ] `docs/reproduction-specification.md` の第 1 部を最新の仕様書に、第 2 部を main の実装（設定・保存のキー・値）に合わせる
- [ ] 第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じであることを確かめる
- [ ] README の内容（機能・コマンド・ファイル構成）が最新か確かめる
- [ ] 残っていること（後でしか確かめられないテストなど）を一覧にして伝える
- [ ] `docs/retrospectives/summary.md` に、WS ごととリリースのふりかえりを YWT でまとめる（9 章）

## 5. 07 の WS の組み方

- epic の優先順位どおりに WS を並べる。**最初の WS は土台**（CI・公開・アプリの骨組み・版の埋め込み・テスト用の入口・check:docs）。
- TASK の依存の順と WS の実施の順を食い違わせない。
- 仕様の変更で足した WS は、すべての WS の「実施の順（x / 全体）」を直す。

## 6. 変更の依頼（いつでも）

開始：オーナーが変更のメモを渡す（何を・なぜ・画面のイメージ）。流れは 2.2 の図。

- [ ] `docs/spec-<版>-<内容>` を切り、`docs/requests/<日付>-spec-<版>-<内容>.md` に依頼日・元のメモ・内容（決めること）・気をつけること・影響の一覧を書く
- [ ] 影響の一覧を示し、進めるか・見送るか・範囲を絞るかを決めてもらう（決めてほしいことは選択肢で聞く。承認まで仕様書を変えない）
- [ ] 仕様書の版を上げ、改訂履歴に書く
- [ ] 影響する承認済みの成果物の版を上げて `review` に戻し、ほかは sources の版の表記だけ直す
- [ ] 承認 → `stable`・`verified` → PR。表の「結果」に PR 番号
- [ ] `docs/spec-<版>-design-plan` で TD・TC・TST を直し、修正用の WS・TASK を足す（すべての WS の実施の順を直す）→ PR
- [ ] TASK を実装（4.3）→ 手動テスト・AC・ふりかえり（4.4）
- [ ] 影響の一覧の全項目に、PR 番号か「直さない理由」を書き、依頼を「完了」にする

### 影響の一覧

| 区分 | 対象 | 直すこと | 結果 |
| :--- | :--- | :--- | :--- |
| 仕様書 | §x | … | PR #n |
| 承認済みの成果物（再承認） | US・GUI など | … | PR #n |
| 承認のない成果物 | TD・TC・TST | … | PR #n |
| 承認のない成果物（足す） | 修正用の WS・TASK | … | PR #n |
| テストのコード／実装 | ファイル | … | PR #n |
| 実施記録 | AC（新しい記録） | … | PR #n |
| 版の表記だけ直すもの | sources を持つ成果物、WS の実施の順 | 表記を直す | PR #n |
| 直さないもの | 承認済みの AC など | 理由（sources の表記は直す） | — |

- 洗い出しは、変わる章を sources に持つ成果物を grep（文字で検索）する。**数値を変えるときは値そのものも grep する**。
- 項目を足したら、同じ部品・画面に触れる項目と見比べ、食い違いを承認の前に直す。
- 画面の配置を変えるときは、手の足し算ではなく、**今の画面を E2E の端末の大きさで測ってから**案を書く。
- 「結果」の列が空いている行が残っていたら、依頼は終わっていない。
- 実装の途中で、承認済みの文書の直し漏れに気づいたら：その文書を `review` に戻し、表に「あとで見つけたもの」の行を足し、再承認を受けてから push する。

## 7. 整合性チェック

### 7.1 段階の前に確かめること

次の段階を始める前（前の段階の承認・PR の前）に確かめる。

**すべての成果物**
- [ ] ID とファイル名が決まりどおりで、欠番を使い直していない
- [ ] sources に、根拠にした成果物の ID と版が書いてある
- [ ] sources の成果物が `stable` で、書いた版が今の版（仕様書は、引用した章がその後の版で変わっていないか）
- [ ] 本文から参照している ID・章番号・ファイルが実在する
- [ ] 上流の版を上げたら、それを sources に持つ下流をすべて見直した（直さないものも版の表記は直した）

**仕様書 → 00**
- [ ] 仕様書の範囲（作るもの・作らないもの）が、そのまま brief の範囲になっている

**00 → 01**
- [ ] brief の前提（サーバーの有無・オフライン・対象端末など）が、ADR か SA で決まっている

**01 → 02**
- [ ] 仕様書の各章が、どれかの US の sources にある（ないものは対象外と理由を書いた）
- [ ] 仕様書の受け入れ基準の各項目が、どれかの US の受け入れ条件になっている
- [ ] US がすべて、どれかの epic に入り、優先順位がある

**02 → 03**
- [ ] 画面に関わる US が、すべてどれかの GUI の sources にある
- [ ] US と GUI の文言（ボタン名・メッセージ）が同じ

**03 → 04**
- [ ] GUI の部品・状態・メッセージを、どのモジュールで作るか決まっている
- [ ] ADR の決定（層の決まり・技術）に反する設計がない

**04 → 05**
- [ ] US の受け入れ条件が、すべて確認 ID に対応している
- [ ] 仕様書の受け入れ基準の各項目に、確認 ID が 1 つ以上ある（一覧にする）
- [ ] 確認 ID ごとに、自動（単体・E2E）か手動か、どのファイルかが決まっている

**05 → 06**
- [ ] すべての確認 ID が、どれかの TASK の対象になっている
- [ ] すべての US が、どれかの WS に入っている
- [ ] TASK の依存の順と、WS の実施の順が食い違っていない

**06 → 07**
- [ ] テストの名前の確認 ID が test-case に実在し、test-case の確認 ID がすべてテストのコードか手動の手順にある

**07 → AC**
- [ ] AC の番号が TASK と同じで、sources に TASK と TC がある
- [ ] TASK の対象の確認 ID が、すべて AC の結果か「確認できなかったこと」にある
- [ ] 結果の数値・文言が、テストの実際の出力と同じ

**完了 → 再現開発仕様書**
- [ ] 第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じ

### 7.2 自動化（check:docs）

7.1 のうち機械で見られるものを、文書の検査のスクリプト（例：`scripts/check-docs.mjs`、`npm run check:docs`）にする。最初の WS で作り、CI の検査にも入れる。

- **エラー**：ID・ファイル名・フォルダ／frontmatter の項目／実在しない ID／sources の版の違い／`stable` なのに sources が `review`／承認のある種類の `stable` に `verified` がない／テストの確認 ID が test-case にない／test-case の確認 ID がテストのコード（自動）か AC（手動）にない
- **厳しいモード**（`--strict`、リリースで使う）：未実装・未記録も 0 に
- 承認待ちの間の「`stable` なのに sources が `review`」は正常（承認で消える）。`review` のまま push すると CI が落ちるので、承認のあとに push する。
- Windows の PowerShell では `npm run x -- --flag` のフラグが届かないことがある。`node scripts/check-docs.mjs --strict` のように直接動かす。

## 8. 段階ごとに先に確かめておくこと（よく手戻りになるもの）

### 8.1 どの技術でも

#### 00〜02

- 仕様書に版と改訂履歴を持たせ、成果物の sources に版を書く。
- 同じ公開先にほかのアプリも載るなら、保存のキー・キャッシュを分けるアプリ識別子を決める。
- アプリの更新の届け方（勝手に切り替えない・「更新」ボタンなど）と、起動に失敗したときの復旧を決める。
- README と、権利・クレジットの表記をいつ作るかを決める（リリースで作るなど）。
- 非機能要件（表示の滑らかさ・入力の遅れなど）も、確かめ方（自動か手動か）まで書く。
#### 03 画面設計

- スマートフォンで、操作する指で大事なものが隠れないか。
- キーボードが出たとき・ノッチ・ホームバー・ホーム画面に入れたアプリのステータスバー。
- アプリの名前がホーム画面で切れないか。
- **画面にアプリの版を出すかと、その場所**。
- 大きさの基準は、**E2E で使う端末の大きさ**も含めて確かめる（自動テストの道具の端末名と、実際の大きさが思ったものと違うことがある。8.2）。
- 大きな文字の日本語（見出しなど）は、狭い画面で折り返したときの区切りを見る（「ー」などが行の頭に来ないか）。

#### 04 詳細設計

- ロジックは画面・時刻・乱数に触れない作り（状態と入力から次の状態を返す関数）にし、単体テストで確かめる。乱数は種を外から渡す。
- 中身を E2E から読めないもの（Canvas など）は、テスト用の入口（`?debug=1`、画面の要素の属性、状態の読み書き・停止・ステップ実行）を設計に入れる。
- 文字の入力欄を置く画面では、ページ全体のキー操作が入力欄で効かないようにする。- 同じ変化を 2 つ以上の部品が受け取り、受け取る順番で結果が変わるとき（例：設定を変えたとき「確認の表示を出す」と「別の部品に知らせる」）は、その順番を詳細設計に書く。書いていないと、作るときに偶然の順番になる。
- 「どこに出すか」（エラー・メッセージ・確認の置き場所）は、仕様書の文とテストケースに 1 つずつ突き合わせてから書く。画面設計から書き写すと、仕様書とずれることがある。

#### 05 テスト

- 実機でしか分からない項目（実機のブラウザ・ホーム画面のアプリ・音・読み上げなど）を、手動のテストケースとして先に一覧にする。**その手順が実機でできるか**まで確かめる（ホーム画面のアプリは URL を変えられない、など）。
- CI と手元でフォントが違うことがある。文字の幅に頼らない。収まりの判定は行の高さを決め打ちにして余裕を残す。
- 「超えたら」「以内」などの境目は、境目ちょうどと 1 つ先の両方を確かめる。- 状態で操作を分けるときは、1 回読んで分けず、端末で分けるか状態が変わるのを待つ。
- テストで画面を開く関数は、前の状態が残らない開き方にする。
- テストを置き換えたら、すぐ check:docs で確認 ID のテストが消えていないかを見る。
- テストで確かめる値（保存のキー・記録など）を、そのテストの中で自分で書かない。アプリが何をしても通るテストになる。
- テストケースで別の確認の手順を借りるとき（「〇〇と同じ操作」）は、その場面で期待する結果が本当に起きるかを、仕様書の決まりに当てはめて確かめる（場面によって、先に別の結果が出ることがある）。
- テストケースの準備に書く例の値（設定・データ・状態）が、ルールの決まり（値の範囲・出てよい組み合わせなど）を満たすかを確かめる。読み込みで直される値だと、画面の文字が例と変わる。
- 画面をまたぐ流れ（前の画面のメッセージを持ち込んで次の画面を開くなど）は、テスト用の入口で場面を直接作らず、実際の操作で通すテストを 1 つは持つ。直接作る場面では、メッセージを出している途中の状態に当たらない。

#### 06 作業計画

- 確認 ID を US の番号で機械的に TASK に割り当てない。PR の前に、**各確認 ID が、その TASK の時点でそろう機能（前の TASK までに作るもの）だけで書けるか** を 1 つずつ点検し、書けないものは機能がそろういちばん早い TASK に移す。あわせて、確認 ID の準備・手順が使う部品（テスト用の共通の操作・画面どうしのつなぎ）が、どれかの TASK の「やること」に入っているかを見る。
- 決まった順で続けて動く処理（乱数を引く順が決まっているなど）は、同じ TASK に入れる。ユーザーストーリーの区切りで分けると、先の TASK で前倒しして作ることになり、設計書を何度も直す。
- 仕様書のファイル構成（README・設定ファイルなど）の各ファイルが、どれかの TASK の「やること」に入っているかを確かめる。入っていないファイルは、リリースの点検まで誰も作らない。

#### 07 実装

- PR の前に、手元で検査と E2E を通す（E2E が build したものを動かすなら、先に build）。
- テスト用の入口で場面を作るときは、確かめたいもの以外を消して前提を先に確かめる。結果の値は決め打ちせず状態から読む。
- 部品を作る TASK と、それを使う画面の TASK が分かれているときは、使う TASK の E2E で、部品の基本の操作（2 行目以降を押す・キーで動かす・無効の項目を選ぶ）を最初に確かめる。部品だけの TASK では、押して確かめる画面がない。
- 表示を更新するときは、押される要素（メニューの行・ボタン）を作り直さず、中身（文字・class・属性）だけを書き替える。押し始めと押し終わりで要素が替わると、クリック・タップが届かない。
- 調べ物・撮影用の一時ファイルは、プロジェクトの外の作業用の一時フォルダに置く。プロジェクトの中に置くと、コミットに混ざるおそれがあり、設定によっては消せない。
- テストの名前は、確認 ID のすぐ後ろに空白を入れる（`test('TC-0000-00 …')`）。編集の道具に渡す文を空白で終わらせない（末尾の空白が落ちて確認 ID が文とつながり、check:docs が数えなくなる）。
- 一覧・スクロールのある画面を作ったら、対象端末の一番小さい大きさ・代表の大きさ・PC の大きさ（例：375 × 667・1280 × 800。オーナーの実機の大きさも加える）で、はみ出し（`scrollHeight − innerHeight` と横の同じ値）を測る。項目の多い場面（一覧が最大の数のときなど）でも測る。写真を見るだけでは、数 px のはみ出しや項目が多いときのはみ出しを見落とす。
- 仕様書に全文があるコードは、行の範囲で切り出して写し（手で打ち直さない）、すぐに型の検査と lint を動かす。仕様書のコードは、このリポジトリの検査の設定で確かめていないことがある。直したところは AC に書く。
- 手元では通る、画面の大きさ・位置を測るテストが CI だけで落ちたら、まず、アプリが描いたあとに直す処理（次のコマ・タイマーで高さを合わせるなど）の前を測っていないかを、直す前と後を 1 つのテストで測って確かめる。CI は手元より遅く、直す前を測ることがある。
- 1 つの画面で、フォーカス・メニューを止める／解くなどの扱いを直したら、同じ作りのほかの画面にも同じ直しが要るかを、その場で確かめる。同じ抜けが別の画面に残る。
- 文書の書き替えは、編集の道具（Edit）を使う。一括の置き換えは、壊れても気づきにくい。書き替えたら `git diff` で全部を見てからコミットする。

### 8.2 技術ごとの注意

#### Web・PWA

- PWA なら、更新の切り替え方（勝手に切り替えない・「更新」ボタン）と、更新の帯は「アプリを開き直したときに出る（開いたままでは出ない）」ことを、手動テストの案内で先に伝える。
- iPhone のタッチは CSS だけでは長押しの虫めがね・2 回タップの拡大が止まらない。操作する場所では `touchstart` の既定の動きと `gesturestart` を止めると決める。
- 日本語の見出しで「ー」などが行の頭に来ないよう、CSS の `line-break: strict` にする。
- スクロールする部品（`overflow: auto`）の中に `position: absolute` の要素（読み上げ用の隠し文など）を置くときは、スクロールする要素を `position: relative` にする。しないと枠で切られず、ページが縦に伸びる。- 全角スペースは、ソースのテンプレート文字列（`` ` `` で囲む文字列）と正規表現に直接書かない（lint の `no-irregular-whitespace` が止める）。ソースでは `String.fromCharCode(0x3000)`、テストの正規表現では `\s` を使う。
- 大きさ・位置を測る前に 2 コマ待つ（`requestAnimationFrame` を 2 回）。

#### Playwright（E2E）

- 端末名と大きさ：「iPhone SE」は第 1 世代の 320 × 568。基準が 375 × 667 なら `iPhone SE (3rd gen)` を使う。
- 時間を進めるテストは、偽の時計を止めてから進める（`clock.install` → `pauseAt` → `runFor`）。`install` だけでは時計が自然に進み、数 ms ずれる。時間で変わる表示は、状態をそろえてから見るか操作の直後に見る。偽の時計はちょうどの時刻のタイマーも動かすので、「超える」と「以上」の違いは境目ちょうどのときにだけ出る。
- `aria-disabled="true"` の要素は「押せるようになるまで」待たれる。無効の項目を押しても何も起きないことを確かめるときは、`click({ force: true })`・`tap({ force: true })` で押す。- 保存を消して開き直すときは、いったん `about:blank` へ移ってから開く。`#` 以降だけが違う URL へは、読み込み直さずに移る（アプリが前の状態を持ったまま）。- アプリのファイルを止めたり差し替えたりするテスト（`page.route`）は、Service Worker を止めて動かす（`test.use({ serviceWorkers: 'block' })`）。Service Worker が保存したファイルを先に出すと、止めたつもりの読み込みが止まらない。
- `setViewportSize` のあとに大きさ・位置を測るときは、`expect.poll` で落ち着くまで待つ。レイアウトが切り替わる幅をまたぐと画面を作り直し、その途中を測ると 0 になる。
- 開き直す場面づくりのあとにイベントの記録を見るときは、その場面のイベントが出るまで待ってから記録を空にし、そこから先だけを見る。開いたときの別のイベントが先に入る。
- 要素があるかどうかを見るときは `page.evaluate` の `querySelector` か `locator.count()` を使う。`locator.evaluate` は要素が出るまで待つので、ループの中で使うと 1 回目で時間切れになる。
- `addInitScript` で仕込んだ記録は、ページを開き直すたびに空になる。場面を作り直すテストでは、場面ごとに記録を見る。
- 手元の E2E が急に時間切れになったら、失敗したときの画面の記録（`test-results/**/error-context.md`）を見て、このアプリが出ているかを確かめる。別のアプリが出ていたら、同じポート（例：Vite の preview は 4173）を別のアプリが使っている（手元では、動いているアプリをそのまま使う設定のときに起きる）。止めてから動かし直す。
- 撮影用の E2E は、作業用の一時フォルダに Playwright の設定ファイル（`testDir: '.'`、`webServer.cwd` にプロジェクト）とテストを置き、`NODE_PATH` にプロジェクトの `node_modules` を指して動かす（設定ファイルは `@playwright/test` を import しない）。

#### Windows・PowerShell

- PowerShell 5.1 では `&&`・`||` が使えない。日本語は BOM なしの UTF-8 のファイルで渡す（1.1）。`npm run x -- --flag` のフラグが届かないときは、スクリプトを `node` で直接動かす（7.2）。
- PowerShell で一括の置き換えをするときは、組を 1 つずつ引数で渡し（配列で 1 組だけ渡すと 1 文字ずつに分かれる）、「見つからなければ止める」を入れ、関数の名前を既存の別名（`R`・`h`・`r` など）と重ねない。

## 9. ふりかえり（YWT）

置き場所：`docs/retrospectives/`（ID・承認なし、check:docs の対象外）。Claude Code が案を書き、オーナーが見て足す。

| いつ | ファイル |
| :--- | :--- |
| WS の終わり | `ws-<番号>.md` |
| リリース | `release.md` |
| 完了 | `summary.md` |

```markdown
# WS-<番号> のふりかえり（<日付>）

対象：<PREFIX>-WS-<番号>（TASK-<番号>〜<番号>、PR #<番号>〜#<番号>）

## 言葉の表
| 言葉 | 意味 |
| :--- | :--- |
| … | … |

## Y（やったこと）
- 前回の T を守れたか（最初に確かめる）
- 終えた TASK と、作った・直したもの
## W（わかったこと）
- うまくいったこと
- つまずいたこと：何が起きたか・なぜ・どうしたか
## T（つぎにやること）
- 次に変えることと、その理由。この文書（8 章など）のどこに足すかも書く
```

- 1 項目 1〜2 行。エンジニアでないオーナーが読むので、**最初に言葉の表**（WS・TASK・PR・確認 ID・CI など、本文に出る専門の言葉の言い換え）を置く。
- T は、次の WS を始める前にこの文書（プロジェクトの写し）に反映し、冒頭の版の表に「追記」の行を足す。
- `summary.md`：Y（全体の数と WS ごとの表）、W（くり返し効いたこと・くり返し出たつまずきとどう直したか）、T（次のプロジェクトで最初から入れること）。
- プロジェクトが終わったら、`summary.md` の T のうちほかのアプリにも効くものを、この文書の次の版（汎用版）に入れる。そのアプリだけの名前・画面・数値は一般の言い方にする。

## 付録 B：言葉の表（解説に使う言い換え）

| 言葉 | 言い換え |
