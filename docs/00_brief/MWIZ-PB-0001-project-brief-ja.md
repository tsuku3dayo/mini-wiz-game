# プロジェクト概要（project-brief）

---

## 1. 目的

ブラウザで遊べる 1 人用のダンジョン探索 RPG「WIZ ～死霊術師の迷宮～」を、スマートフォンで手軽に遊べるアプリ（PWA）として作る。元の WIZ（React + NestJS + PostgreSQL でローカルに動かしていたもの）のルール・数値・文言・音を変えずに、サーバーなしでブラウザだけで動く形に作り直し、公開 URL から誰でも遊べるようにする。

あわせて、`mini-blockbreaking-game` で回した開発のフロー（仕様書 → 段階ごとの承認 → 設計・テスト・実装、`docs/workflow.txt`）を、より大きな題材（仕様書 約 4,800 行）でもう一度回して確かめる。

## 2. 作るもの

| 項目 | 内容 |
| --- | --- |
| 名前 | WIZ ～死霊術師の迷宮～（ページの題名）。タイトル画面の見出しは「WIZ」と副題「～ 死霊術師の迷宮 ～」、ホーム画面のアプリ名は「WIZ」 |
| 形 | ブラウザで動き、ホーム画面に追加できるアプリ（PWA）。サーバーなし・通信なし。一度開いた後は通信なしでも遊べる |
| 遊び方 | 宿屋を拠点に、出発ごとにランダムに作られる 5 階層（各 10×10）のダンジョンを疑似3D（一人称のワイヤーフレーム）で探索する。敵と戦ってレベルを上げ、敵が落とす装備を集め、5F のボス「暗黒のネクロマンサー」を倒すとクリア。クリアの後も同じキャラクターで次の周を遊べる |

| 想定する端末 | スマートフォンの縦画面（iPhone の Safari、Android の Chrome）を基準にし、タップで遊べる。PC の Chrome / Edge ではキーボードだけ、またはマウスでも遊べる。**画面はスマートフォンの表示を最優先する** |

## 3. 想定する利用者

- スマートフォンで、すき間の時間に少しずつ探索を進める人（1 回の出撃は数分〜十数分。宿屋でセーブして中断できる）。
- 昔ながらのダンジョン RPG（ウィザードリィ風の一人称の迷宮・コマンド選択の戦闘）が好きな人。
- 装備を集めて強くし、周回して実績を増やすのを楽しむ人（記録はその端末の中だけ。ほかの人とは競わない）。
- 公開 URL を開くだけで遊べ、登録・インストールは不要（インストールは任意）。

## 4. 範囲

仕様書 v1.1 §1.1 の範囲をそのまま範囲にする。

### 4.1 含めるもの

- 仕様書 v1.1 に書かれたすべての機能（元の WIZ の MVP〜Update6 の機能と、v1.1 で足したインストール・オフライン・更新・起動の復旧）。
  - キャラクターの作成と成長、ダンジョンの生成、探索、戦闘、敵、回復、装備・所持品・ドロップ、クリア・周回・実績、セーブとつづきから、画面と画面遷移、メッセージと演出、効果音と BGM、敵の絵、ゲーム API、端末内保存、インストール・オフライン・更新、数値パラメータ、乱数を引く順序
- 仕様書の受け入れ基準（§16）をすべて満たすこと。
- 単体テスト（Vitest）・画面テスト（Playwright の E2E、アクセシビリティの検査を含む）と、GitHub Actions による自動確認。
- GitHub Pages への自動公開。
- README（遊び方・起動方法・テスト・ファイル構成）。
- 完了後の再現開発仕様書（`docs/reproduction-specification.md`）。

### 4.2 含めないもの

仕様書 v1.1 §1.1 の「作らない」と同じ。

- ログイン・複数ユーザー、複数のセーブスロット。
- サーバー・DB・通信（ほかの端末との共有・ランキング）。
- 記録の書き出し・読み込み（ファイルへのバックアップ）。
- ゲームエンジン・3D ライブラリ・UI フレームワーク、音声ファイル。
- 横画面の専用レイアウト（横向きや PC では、幅 600px 以上の広い画面の配置になる）。

仕様書のほかの章で決まっていて、作らないもの：

- フォントの同梱（端末のフォントを使う。仕様書 §11.3）。
- 元の WIZ のデータ（DB のセーブ）を持ち込む手段（仕様書 §21.4）。

## 5. 前提と制約

| 区分 | 内容 |
| --- | --- |
| 構成・技術 | `mini-blockbreaking-game` と同じ構成にする：Vite + TypeScript（UI フレームワークなし）+ vite-plugin-pwa + Vitest + Playwright + ESLint、Node.js 24。仕様書 v1.1 第 2 部に案がある。01 で ADR として決める |
| ルールの作り | ルールは純粋関数で、乱数源 `Rng` を引数で受け取る（同じシードなら同じダンジョン・同じ戦闘結果）。画面はブラウザの中の「ゲーム API」を通してだけ状態を変え、ゲームの値を計算しない（仕様書 §1.3・§1.4） |
| 画面 | スマートフォンの縦画面での表示を最優先する。配置は 03 の試作を実機で触って決める（仕様書 §11.1） |
| 公開 | GitHub Pages（GitHub アカウント `tsuku3dayo`）。公開 URL は https://tsuku3dayo.github.io/mini-wiz-game/ 。リポジトリは https://github.com/tsuku3dayo/mini-wiz-game （公開）。同じサイト（`tsuku3dayo.github.io`）に `mini-blockbreaking-game` などほかのアプリも載るので、保存のキー・キャッシュをアプリ識別子で分ける |
| 通信・個人情報 | 外部へデータを送らない。名前は端末の中にだけ保存する |
| 素材 | 画像は敵の絵 6 枚（元の WIZ の PNG をオーナーが持ち込む。利用条件・公開してよいかはオーナーが確かめる）とアイコン（スクリプトで作る）。音はコードで合成する。フォントは端末のもの。外部のフォント・スクリプト・CDN に頼らない |
| 変えないもの | ゲームのルール・数値・乱数を引く順序・画面の文言・効果音の音色・BGM の曲データ（仕様書 v1.0 から変えていない） |
| 環境 | Node.js v24.0.0・npm 11.3.0・Git 2.51.0・GitHub CLI はインストール済み。リポジトリは Git 管理済みで、GitHub に push 済み |

## 6. 成功の基準

- 仕様書 §16 の受け入れ基準をすべて満たす（自動テストか手動テストで確認した記録がある）。
- `npm run verify`（lint → 成果物の整合性 → 単体テスト → build → 成果物の検査）と E2E が CI で通る。
- 通しプレイ（固定シードでボス撃破まで、装備を拾ってクリア、2 周）の自動テストが通る。
- 公開 URL を iPhone と Android の実機で開き、インストール・通信なしの起動・ボス撃破までのプレイ・セーブとつづきからができる。スマートフォンの画面で、はみ出し・指で隠れる・押しにくいがない。
- 各段階の成果物がオーナーに承認されている。

## 7. 進め方

各段階の成果物は `docs/` の段階ごとのフォルダに、ID 付きの Markdown で置く。ID・ファイル名・frontmatter の決まりは [`CLAUDE.md`](../../CLAUDE.md) の「成果物の書式」に従う。「承認」の地点では、オーナーの承認を得るまで次の段階に進まない。手順は [`workflow.txt`](../workflow.txt)。

| 段階 | 成果物（ID の種類） | フォルダ | 承認 |
| --- | --- | --- | --- |
| 00 プロジェクト概要 | project-brief（PB） | `docs/00_brief/` | ○ |
| 01 システム構成 | system-architecture（SA）、technology-stack（TS）、architecture-decision（ADR） | `docs/01_architecture/` | ○ |
| 02 要件・ユーザーストーリー | epic（EP）、user-story（US） | `docs/02_requirements/` | ○ |
| 03 画面設計 | gui-design（GUI）、試作（`prototype/`、公開 URL で実機で触る） | `docs/03_gui/` | ○ |
| 04 詳細設計 | technical-design（TD） | `docs/04_design/` | — |
| 05 テスト（06 と並行） | test-strategy（TST）、test-case（TC） | `docs/05_test/` | — |
| 06 作業計画（05 と並行） | workstream（WS）、implementation-task（TASK） | `docs/06_plan/` | — |
| 07 実装・自動テスト | ソースコード、自動テスト、CI | リポジトリ直下 | — |
| 手動テスト | 手動テストの結果（attested-computation に含める） | — | ○ |
| 最終 | attested-computation（AC） | `docs/07_attested/` | ○ |

- **attested-computation** は、実装タスクが「実装して検証まで終えた」ことの記録である。implementation-task（何をやるか）と test-case（どう確かめるか）に対して、「実際にやって確かめた結果」を残す。中身は、実施概要（タスク・実施者・環境）、テストケースの手順ごとの結果、**確認できなかったこと**、後片付け、完了定義のチェックリスト。Claude Code が書き、オーナーが中身を確かめて承認したら確定する（承認者と日時を記録する）。
- 仕様が大きいので、02 の epic を機能のまとまり（仕様書の元のフェーズ MVP〜Update6 が目安）で分け、07 の WS を細かくする。最初の WS は土台（CI・公開・PWA の骨組み）にする。

## 9. リスクと対策

| リスク | 対策 |
| --- | --- |
| スマートフォンの縦画面に収まらない（ダンジョン画面は、疑似3D・移動ボタン・地図・ステータス・メッセージを縦に積むと 1 画面を超える見込み） | スマートフォンの表示を最優先する。03 で試作を作って公開 URL に置き、実機で触って配置を決める。仕様書の配置と違えば、変更の依頼で仕様書の版を上げる |
| タッチの操作感（指で疑似3D・メッセージが隠れる、移動ボタンを押し間違える、メッセージのスキップと決定の取り違え） | 03 の試作で確かめる。ボタン 48px・メニューの行 44px 以上（仕様書 §11.11）。手動テストで確かめ、必要なら値を調整する |
| 端末のフォントで見え方が変わる（iPhone には日本語の等幅フォントがなく、桁や枠がずれる） | 数字は等幅で出す（`tabular-nums`）。字の幅に頼った配置にしない。03 の試作で iPhone・Android の実機で確かめる |
| 仕様の量が多く、書き写しや乱数の順序の誤りが入る | ルールは仕様書の数値の例（§16 の受け入れ基準・参考値）で単体テストする。乱数は `SequenceRng` で消費順を確かめ、`SeededRng(2026)` の参考値と突き合わせる。BGM の曲データは仕様書のコードを正本にして、テストと実機で聴いて確かめる |
| 実装の量が多く、途中で手戻りが起きる | WS を機能のまとまりで細かくし、各 WS の終わりに公開 URL で手動テストする。設計と違う作りにしたら、TD・GUI を直す |
| iPhone で記録（プレイ中の状態・セーブ）が消える | 起動時に `navigator.storage.persist()` を頼む。ホーム画面に追加すると消えにくいことを案内する。書き出し・読み込みは範囲外（必要になったら変更の依頼にする） |
| スマートフォンで効果音・BGM が鳴らない | 最初のタップで音を使える状態にする（受ける入力を `mini-blockbreaking-game` と同じに増やした。仕様書 §12.1）。鳴らなくてもゲームは動く。実機で聴いて確かめる |
| 古いキャッシュで起動しなくなる | `mini-blockbreaking-game` と同じ起動失敗からの復旧の仕組みを入れる（仕様書 §30.4） |
| 敵の絵が届かない・公開できない | 絵がなくても敵の名前だけで戦闘画面が動く（仕様書 §13.2）。届いたら MD5 で確かめて入れる。公開してよいかはオーナーが確かめる |
| 公開版でも `?debug=1` で地図全体が見える | 1 人用で競う相手がいないので受け入れる（仕様書 §28） |
| 同じサイトのほかのアプリと保存・キャッシュが混ざる | 保存のキーを `mini-wiz-game-` で始め、起動の復旧はこのアプリの範囲だけを消す（仕様書 §21.2・§30.4）。01 でアプリ識別子を ADR にする |
