## 1. 基本の決まり

| 決まり | 内容 |
| :--- | :--- |
| 指示で進む | Claude Code は、オーナーの指示なしに次の工程へ進まない |
| 承認はチャットで | 「承認します」「OK」で受ける。はっきりしない返事は確かめる |
| PR ごとに区切る | 作業はブランチ → PR → CI が緑 → オーナーがマージ |
| マージ = 公開 | main へのマージで公開される。アプリが変わる PR は、そう伝えてからマージを頼む |
| マージ後の片付け | **`gh pr view <番号> --json state` が `MERGED` であることを確かめてから**、main を pull し、作業ブランチを手元と GitHub から消し、公開の実行と公開 URL を確かめる（オーナーの次の指示を、マージの合図と思い込まない。未マージの枝を消すと PR が閉じる） |
| 名前の扱い | 了承をとっていない人の名前を公開リポジトリに書かない |
| 日本語で書く | Claude Code のメッセージ・コミットメッセージ・PR は、できる限り日本語（1.1） |
| 解説を付ける | エンジニアでないオーナーにも分かるように書く（1.1） |
| コマンドにリスク評価 | PowerShell などのコマンドを動かす前にオーナーへ確認を求めるとき、コマンドの説明の頭に「【リスク：低／中／高（理由）】」を書く。低＝読むだけ（状態・ファイルを見る、テスト）、中＝手元のファイルを書き替える・作る（取り消せる。コミット・build など）、高＝GitHub に送る・消す・元に戻しにくい（push・PR・ブランチの削除など）。1 つのコマンドに複数あれば、いちばん高いものを書く（WS-0008 のふりかえり。オーナーの指示）。**ファイルの削除（`Remove-Item` など）は、自分が作った一時ファイルでも「高」**。消さずに済むなら作業用フォルダへ移す（中）（WS-0016 のふりかえり：「中」と表示して 3 回拒否された） |

### 1.1 言葉と解説

**日本語で書くもの**
- Claude Code のメッセージ
- コミットメッセージ。1 行目に何をしたかを短く書き、必要なら 1 行空けて理由を書く（1 コミット 1 目的）
- PR の題名・本文・コメント

**英数字のままにするもの**：ブランチ名・ID・ファイル名・コマンド。日本語にすると、道具によって文字化けしたり、入力しにくくなったりする。

**解説の付け方**
- 専門の言葉（ブランチ・PR・マージ・CI など）は、はじめて出たところで短く言い換える（例：「PR（変更を本流に入れてよいか確かめてもらう申請）」）。
- 何をしたかだけでなく、なぜそうしたか・オーナーにとって何が変わるか・次に何をしてほしいかを書く。
- コマンドやファイル名をただ並べない。必要なものだけ示し、意味を添える。
- 承認を求めるときは、決めてほしいことを選択肢と推奨で示し、選んだあとに何が起きるかを添える。

**文字化けを防ぐ**（Windows の PowerShell 5.1）：日本語のコミットメッセージ・PR の本文は、BOM なしの UTF-8 のファイルに書いて渡す（`git commit -F <ファイル>`、`gh pr create --body-file <ファイル>`）。GitHub でマージしたときに自動で付く題名（「Merge pull request #n …」）は英語になる。日本語にしたいときは、マージの画面で書き換えるか、リポジトリの設定で PR の題名を使うようにする。

## 2. 開発工程のフロー

### 2.1 全体の流れ

`［ ］` はオーナーが出す指示、`◆` はオーナーの承認。

```
          仕様書（doc/specification.md）
                     │
                     ▼  ［仕様書をもとに project-brief を作ってください］
┌──────────────────────────────────────┐
│ 00 プロジェクト概要                  │  project-brief
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［01 システム構成を作ってください］
┌──────────────────────────────────────┐
│ 01 システム構成                      │  system-architecture
│                                      │  technology-stack
│                                      │  architecture-decision
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［02 要件・ユーザーストーリーを作ってください］
┌──────────────────────────────────────┐
│ 02 要件・ユーザーストーリー          │  epic（優先順位 = 07 の WS の順）
│                                      │  user-story
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［03 画面設計を作ってください］
┌──────────────────────────────────────┐
│ 03 画面設計                          │  gui-design
│                                      │  試作（公開 URL に置き、実機で触る）
└──────────────────────────────────────┘
                     │  ◆ 承認（試作を実機で触ってから）
                     ▼  ［実行してください］
┌──────────────────────────────────────┐
│ 04 詳細設計                          │  technical-design
└──────────────────────────────────────┘
            ┌────────┴────────┐
            ▼                 ▼
┌───────────────────┐ ┌───────────────────┐
│ 05 テスト         │ │ 06 作業計画       │
│  test-strategy    │ │  workstream       │
│  test-case        │ │  impl-task        │
└───────────────────┘ └───────────────────┘
            └────────┬────────┘
                     │  ※ 04〜06 は承認なし。段階ごとに「進めてよいか」→ PR
                     ▼  ［WS-<番号> を始めてください］
┌──────────────────────────────────────┐
│ 07 実装・自動テスト                  │◀─────┐
│   TASK ごとに：                      │      │
│   ブランチ → テスト → 実装 → PR      │      │
│   → CI が緑 → マージ（= 公開）       │      │
│   → attested-computation（draft）    │      │ 次の WS
└──────────────────────────────────────┘      │
                     │                        │
                     ▼                        │
┌──────────────────────────────────────┐      │
│ 手動テスト（WS の終わり、実機）      │      │
│   attested-computation（review）     │      │
│   ふりかえり（ws-<番号>.md）         │      │
└──────────────────────────────────────┘      │
                     │  ◆ 承認 ───────────────┘
                     │
                     ▼  最後の WS が終わったら ［リリースしてください（版）］
┌──────────────────────────────────────┐
│ リリース                             │  版の確定・README
│   マージ（= 公開）→ 全体の手動テスト │  attested-computation
│                                      │  ふりかえり（release.md）
└──────────────────────────────────────┘
                     │  ◆ 承認
                     ▼  ［再現開発仕様書を最新にしてください］
┌──────────────────────────────────────┐
│ 完了                                 │  再現開発仕様書
│                                      │  ふりかえりのまとめ（summary.md）
└──────────────────────────────────────┘
```

### 2.2 途中で仕様を変えるとき（変更の依頼。いつでも）

```
［変更のメモ（何を・なぜ・画面のイメージ）］
                     │
                     ▼
┌──────────────────────────────────────┐
│ 変更の依頼を書く                     │  doc/requests/<日付>-spec-<版>-<内容>.md
│   内容・影響の一覧                   │  （直す成果物・テスト・コード）
└──────────────────────────────────────┘
                     │  ◆ 進めるか・見送るか・範囲を絞るか
                     ▼
┌──────────────────────────────────────┐
│ 仕様書の版を上げる                   │
│ 影響する承認済みの成果物を review に │  PB・ADR・US・GUI など
└──────────────────────────────────────┘
                     │  ◆ 承認 → PR
                     ▼
┌──────────────────────────────────────┐
│ 設計・テスト・計画を直す             │  TD・TC・TST
│ 修正用の WS・TASK を足す             │  WS・TASK → PR
└──────────────────────────────────────┘
                     │
                     ▼
       07 実装 → 手動テスト → ◆ 承認（2.1 と同じ）
                     │
                     ▼
       影響の一覧の「結果」をすべて埋めて「完了」
       （完了のあとに変えたときは、再現開発仕様書の第 1 部も直す）
```

## 3. 成果物

### 3.1 種類と置き場所

ID は `<PREFIX>-<種類>-<4 桁>`、ファイル名は `<ID>-<種類名>-ja.md`。欠番は使い直さない。

| 工程 | 種類 | 略 | 置き場所 | 承認 |
| :--- | :--- | :--- | :--- | :--- |
| 00 | project-brief | PB | doc/00-project-brief | あり |
| 01 | system-architecture / technology-stack / architecture-decision | SA / TS / ADR | doc/01-system | あり |
| 02 | epic / user-story | EP / US | doc/02-requirements | あり |
| 03 | gui-design | GUI | doc/03-gui | あり |
| 04 | technical-design | TD | doc/04-design | なし |
| 05 | test-strategy / test-case | TST / TC | doc/05-test | なし |
| 06 | workstream / implementation-task | WS / TASK | doc/06-plan | なし |
| 07 | attested-computation（実施記録） | AC | doc/07-attested | あり |

ID のない文書：変更の依頼 `doc/requests/`、ふりかえり `doc/retrospectives/`、再現開発仕様書 `doc/reproduction-specification.md`。

### 3.2 frontmatter

```yaml
---
id: <PREFIX>-US-0001
type: user-story
title: タイトル画面から始める
status: review          # draft | review | stable
version: 1.0
updated: 2026-01-01
sources:                # 根拠にした成果物と、その版
  - <PREFIX>-EP-0001（v1.0）
  - doc/specification.md (v1.0) §7
verified: null          # 承認したら { by, at（+09:00） }
---
```

### 3.3 番号の決まり

- test-case の番号は user-story と同じ。AC の番号は TASK と同じ。
- TASK のない記録（リリース・完了）に AC の番号を使ったら、次の TASK はその番号を飛ばし、TASK と AC の番号をそろえる（WS-0011 のふりかえり）。
- 確認 ID は `<PREFIX>-TC-<4 桁>-<2 桁>`。自動テストは名前の先頭に確認 ID を書く。
- 非機能の test-case の番号の付け方は、05 の最初に決める（あとから足すストーリーとずれないように）。

### 3.4 版の上げ方

| 場合 | すること |
| :--- | :--- |
| 中身が変わる | 版を 0.1 上げる。承認のある種類は `status: review`・`verified: null` に戻し、再承認 |
| 上流の版が上がったが、中身は変わらない | sources の版の表記だけ直す（版・status・verified はそのまま） |

版の上げと、全成果物の sources の表記そろえは、スクリプト（`scripts/`）で行う。最初から用意しておく。

## 4. 工程ごとの進め方

### 4.1 承認のある文書（00〜03）

- [ ] main を最新にし、`docs/<工程>-<内容>` を切る
- [ ] 入力の成果物を読み、決めてほしいことがあれば、選択肢と推奨を示して先に聞く
- [ ] 成果物を `status: review` で書く
- [ ] 整合性チェック（7 章）を確かめ、check:docs を通す
- [ ] 03 では、試作を公開 URL に置き、実機で触ってもらう（下の「03 の試作」）
- [ ] コミットし、要点と決めてほしいことを解説つきで短く示して承認を求め、止まる（push はまだしない）
- [ ] 承認を受けたら `status: stable`・`verified` を書いてコミット
- [ ] push して PR（本文に成果物の ID・版・承認日時）→ CI が緑 → マージを頼む
- [ ] マージされたら片付け（1 章）

| 工程 | 開始の指示（渡すもの） |
| :--- | :--- |
| 00 | 「仕様書をもとに project-brief を作ってください」（仕様書、対象の端末、公開先） |
| 01 | 「01 システム構成を作ってください」（流用するもの、使いたい／使いたくない技術） |
| 02 | 「02 要件・ユーザーストーリーを作ってください」（優先順位の付け方） |
| 03 | 「03 画面設計を作ってください」（参考の画面、基準の端末） |

**03 の試作**：画面の大きさ・配置と主な操作だけの HTML を `prototype/` に置き、公開 URL で実機で触ってもらう。本物とは**名前・アイコンを変える**（取り違え防止）。確かめること：指で大事なものが隠れない／ボタン 44 px 以上／一番小さい端末で 1 画面に収まる／キーボード・ノッチ・ホームバー／ホーム画面で名前が切れない／文字が読める。

### 4.2 承認のない文書（04〜06）

- [ ] 始める前に「進めてよいか」を確かめ、「実行してください」を受けてから `docs/<工程>-<内容>` を切る
- [ ] 成果物を書き、整合性チェック（7 章）を確かめ、check:docs を通す
- [ ] `status: stable`・`verified: null` でコミット → PR → CI が緑 → マージを頼む

### 4.3 07 実装（TASK ごと）

開始：「WS-<番号> を始めてください」

- [ ] main を最新にし、TASK の文書に書いた名前でブランチを切る（`feat/<TASK>-<内容>`。直しは `fix/…`、道具は `chore/…`）
- [ ] TASK の「やること」と対象の確認 ID を読む。WS の最初の TASK では、WS の全 TASK について、「やること」に書いた道具（自動プレイヤーなど）が使う機能も、その TASK の時点でそろうかを確かめる（確認 ID の点検だけでは漏れる）
- [ ] テスト（名前の先頭に確認 ID）を書く → 実装する
- [ ] 手元で `npm run verify`（lint・単体・build・dist の検査・check:docs）と E2E を通す
- [ ] check:docs の「テストのコードに N」が、その TASK の自動の確認 ID の数だけ増えたかを確かめる（確認 ID が数えられていなくても、注意の数だけでは気づけない）
- [ ] 画面の変更は、PC と一番小さいスマートフォンの幅でスクリーンショットを見る
- [ ] 設計と違う作りにしたら TD・GUI を直す（承認済みのものは再承認）
- [ ] AC（draft）に自動テストの結果を書き、同じ PR に入れる
- [ ] 公開版に、途中までしか遊べない場面（まだ作っていない画面へ進むなど）が残るときは、PR とオーナーへの報告に、その場面と抜け方を書く
- [ ] PR → CI が緑 → マージを頼む（マージ = 公開）

### 4.4 WS の終わり（手動テスト）

- [ ] 版の切り替えを確かめる WS では、最後の TASK をマージする**前に**、実機で今の版を一度開いてもらう
- [ ] 実機の確認の手順と「見ることの一覧」は、マージ（公開）の**前に**渡す。公開のあとでは、手順の前半（セーブ・ダンジョンを歩くなど）をやり直せない。PWA の更新では「帯は、アプリを開き直したときに出る（開いたままでは出ない）」ことも先に伝える（WS-0006 のふりかえり）
- [ ] 実機の確認を頼むときは、確認ごとに「OK／NG／見ていない」を書き込める返事のひな形を付ける（端末が 2 つなら端末ごとに）。まとめた返事でも、AC に確認ごとの結果を残せるようにするため（WS-0009 のふりかえり）
- [ ] 実機ではすぐに行けない場面（レアなドロップ・ボスなど）は、`?debug=1` の開発者ツールのコンソールに貼るだけで作れるコードを用意し、**手元で Playwright で動かしてから**手順と一緒に渡す（WS-0007 のふりかえり）
- 実機の確認で端末の機能（読み上げ・ホーム画面への追加など）を使うときは、オンにする手順と元に戻す方法を案内に付ける。iPhone の Safari には開発者ツールのコンソールがないので、コンソールが要る手順は PC で行うか、案内から外して AC の「確認できなかったこと」に書く（WS-0010 のふりかえり）
- [ ] 実機の確認を、テストケースの手順の一部にしぼって頼むときは、しぼった理由と「今回は見ない手順」を案内に書き、AC の「確認できなかったこと」にも書く（WS-0011 のふりかえり）
- [ ] 返事のひな形には、どの絵・どの版・どの場面を見たかが分かる欄（見た敵の名前など）を付け、空いていたら聞き返す。まとめた返事だけでは、AC にどの結果かを書けない（WS-0012 のふりかえり）
- [ ] WS の TASK がすべてマージ・公開されたことを確かめる
- [ ] 手動テストを案内する。**最初に「どのアプリで確かめるか」**（公開 URL か、ホーム画面の本物か試作か）を確かめてもらう
- [ ] 実機ではすぐに行けない場面（ボス・持ち物が満杯など）を案内の中で先に挙げ、探さなくてよいと伝える。その場面は E2E とスクリーンショットで確かめたと AC の「確認できなかったこと」に書く
- [ ] 結果（OK、または NG と様子・スクリーンショット）を受け取る。結果なしの「承認」は、結果を先に確かめる
- [ ] `docs/ws-<番号>-ac` で、AC に手動の結果と「確認できなかったこと」（持っていない端末など）を書き `review` に
- [ ] 同じブランチで、ふりかえりの案（9 章）を書いて見てもらう
- [ ] 承認を受けたら `stable`・`verified` → ふりかえりの T をこの文書に反映 → PR → マージを頼む
- [ ] 次の WS は、指示を受けてから始める

実機で原因が分からないときは、推測で直すのは 1 回まで。次は、画面に状態を出す一時的な診断を入れ、記録を見て決める（WS を閉じる前に消す）。

### 4.5 リリース

開始：「リリースしてください」（バージョン番号）

- [ ] `package.json` の version を決め、画面の版の表示を確かめる
- [ ] 仕様書の受け入れ基準のすべてに、確認 ID と結果があることを一覧で確かめる
- [ ] check:docs を厳しいモード（未実装・未記録も 0）で通す
- [ ] README（使い方・権利やクレジットの表記）がそろっているか確かめる
- [ ] 「マージ = 公開」と伝え、公開前に入れたいものがないか聞いてから、マージを頼む
- [ ] 公開後に、全体の手動テストを案内する → AC を review → 承認 → PR
- [ ] AC と同じ PR に、リリースのふりかえり `release.md` を入れる

リリースの AC には TASK がないので、最後の TASK の次の番号にし、その理由を AC に書く（リリース 1.0.0 のふりかえり）。

リリースで画面や仕様に足りないものが見つかったら、変更の依頼（6 章）として修正用の WS・TASK を足し、その TASK の PR をリリースの PR にする。

### 4.6 完了

開始：「再現開発仕様書を最新にしてください」

- [ ] `doc/reproduction-specification.md` の第 1 部を最新の仕様書に、第 2 部を main の実装（設定・保存のキー・値）に合わせる
- [ ] 第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じであることを確かめる
- [ ] README の内容（機能・コマンド・ファイル構成）が最新か確かめる
- [ ] 残っていること（後でしか確かめられないテストなど）を一覧にして伝える
- [ ] `doc/retrospectives/summary.md` に、WS ごととリリースのふりかえりを YWT でまとめる（9 章）

## 5. 07 の WS の組み方

- epic の優先順位どおりに WS を並べる。**最初の WS は土台**（CI・公開・PWA の骨組み・版の埋め込み・テスト用の入口）。
- TASK の依存の順と WS の実施の順を食い違わせない。
- 仕様の変更で足した WS は、すべての WS の「実施の順（x / 全体）」を直す。

## 6. 変更の依頼（いつでも）

開始：オーナーが変更のメモを渡す（何を・なぜ・画面のイメージ）。流れは 2.2 の図。

- [ ] `docs/spec-<版>-<内容>` を切り、`doc/requests/<日付>-spec-<版>-<内容>.md` に依頼日・元のメモ・内容（決めること）・気をつけること・影響の一覧を書く
- [ ] 影響の一覧を示し、進めるか・見送るか・範囲を絞るかを決めてもらう（決めてほしいことは選択肢で聞く。承認まで仕様書を変えない）
- [ ] 仕様書の版を上げ、改訂履歴に書く
- [ ] 影響する承認済みの成果物の版を上げて `review` に戻し、ほかは sources の版の表記だけ直す
- [ ] 承認 → `stable`・`verified` → PR。表の「結果」に PR 番号
- [ ] `docs/spec-<版>-design-plan` で TD・TC・TST を直し、修正用の WS・TASK を足す（すべての WS の実施の順を直す）→ PR
- [ ] TASK を実装（4.3）→ 手動テスト・AC・ふりかえり（4.4）
- [ ] 影響の一覧の全項目に、PR 番号か「直さない理由」を書き、依頼を「完了」にする

### 影響の一覧

| 区分 | 対象 | 直すこと | 結果 |
| :--- | :--- | :--- | :--- |
| 仕様書 | §x | … | PR #n |
| 承認済みの成果物（再承認） | US・GUI など | … | PR #n |
| 承認のない成果物 | TD・TC・TST | … | PR #n |
| 承認のない成果物（足す） | 修正用の WS・TASK | … | PR #n |
| テストのコード／実装 | ファイル | … | PR #n |
| 実施記録 | AC（新しい記録） | … | PR #n |
| 版の表記だけ直すもの | sources を持つ成果物、WS の実施の順 | 表記を直す | PR #n |
| 直さないもの | 承認済みの AC など | 理由（sources の表記は直す） | — |

- 洗い出しは、変わる章を sources に持つ成果物を grep する。**数値を変えるときは値そのものも grep する**。
- 項目を足したら、同じ部品・画面に触れる項目と見比べ、食い違いを承認の前に直す。
- 画面の配置を変えるときは、手の足し算ではなく、**今の画面を E2E の端末の大きさで測ってから**案を書く。
- 「結果」の列が空いている行が残っていたら、依頼は終わっていない。
- 「結果」の列などに PR の番号を書くのは、PR を作ってから。番号は、ほかの人の PR や Dependabot の PR で先に使われることがある（WS-0012 のふりかえり）。
- 実装の途中で、承認済みの文書の直し漏れに気づいたら：その文書を `review` に戻し、表に「あとで見つけたもの」の行を足し、再承認を受けてから push する。
- 公開したら、その WS の実機の確認をすぐ案内し、次の変更の依頼を始める前に結果をもらう。待っている確認があるのに新しい依頼を受けるときは、依頼書に「待っている確認をどう引き継ぐか」を書いて、オーナーに決めてもらう。確認が何度も送られると、記録が長く draft のままになり、引き継ぎの記入が増える（WS-0016 のふりかえり：v1.7 の効果音の確認が v1.9・v1.10 と 2 回送られた）。
- 承認済みの US に受け入れ条件を足すときは、末尾に足す。途中に足すと、テストケースの「条件」の番号が全部ずれる（WS-0016 のふりかえり）。
- オーナーが用意した素材（画像など）を置く前に、形式（大きさ・色の種類・透明の有無）と、ファイルに入っている説明の情報（EXIF・テキストのチャンクなど。公開リポジトリに置くため）を調べる。決まりに合わないときは、見本（画面の背景の上に並べた画像など）を作って選んでもらう（WS-0017 のふりかえり：v4 の敵の絵は背景が黒で透明がなかった）。
- 加工の案を見せるときは、加工しきれずに残る部分（例：外側の黒だけを透明にしたときの、絵に囲まれたすき間の黒）も数えて伝える。決める前に分かるようにするため（WS-0017 のふりかえり）。

## 7. 整合性チェック

### 7.1 段階の前に確かめること

次の段階を始める前（前の段階の承認・PR の前）に確かめる。

**すべての成果物**
- [ ] ID とファイル名が決まりどおりで、欠番を使い直していない
- [ ] sources に、根拠にした成果物の ID と版が書いてある
- [ ] sources の成果物が `stable` で、書いた版が今の版（仕様書は、引用した章がその後の版で変わっていないか）
- [ ] 本文から参照している ID・章番号・ファイルが実在する
- [ ] 上流の版を上げたら、それを sources に持つ下流をすべて見直した（直さないものも版の表記は直した）

**仕様書 → 00**
- [ ] 仕様書の範囲（作るもの・作らないもの）が、そのまま brief の範囲になっている

**00 → 01**
- [ ] brief の前提（サーバーなし・オフライン・対象端末など）が、ADR か SA で決まっている

**01 → 02**
- [ ] 仕様書の各章が、どれかの US の sources にある（ないものは対象外と理由を書いた）
- [ ] 仕様書の受け入れ基準の各項目が、どれかの US の受け入れ条件になっている
- [ ] US がすべて、どれかの epic に入り、優先順位がある

**02 → 03**
- [ ] 画面に関わる US が、すべてどれかの GUI の sources にある
- [ ] US と GUI の文言（ボタン名・メッセージ）が同じ

**03 → 04**
- [ ] GUI の部品・状態・メッセージを、どのモジュールで作るか決まっている
- [ ] ADR の決定（層の決まり・技術）に反する設計がない

**04 → 05**
- [ ] US の受け入れ条件が、すべて確認 ID に対応している
- [ ] 仕様書の受け入れ基準の各項目に、確認 ID が 1 つ以上ある（一覧にする）
- [ ] 確認 ID ごとに、自動（単体・E2E）か手動か、どのファイルかが決まっている

**05 → 06**
- [ ] すべての確認 ID が、どれかの TASK の対象になっている
- [ ] すべての US が、どれかの WS に入っている
- [ ] TASK の依存の順と、WS の実施の順が食い違っていない

**06 → 07**
- [ ] テストの名前の確認 ID が test-case に実在し、test-case の確認 ID がすべてテストのコードか手動の手順にある

**07 → AC**
- [ ] AC の番号が TASK と同じで、sources に TASK と TC がある
- [ ] TASK の対象の確認 ID が、すべて AC の結果か「確認できなかったこと」にある
- [ ] 結果の数値・文言が、テストの実際の出力と同じ

**完了 → 再現開発仕様書**
- [ ] 第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じ

### 7.2 自動化（`npm run check:docs`）

`scripts/check-docs.mjs` を最初の WS で作り、CI の verify にも入れる。

- **エラー**：ID・ファイル名・フォルダ／frontmatter の項目／実在しない ID／sources の版の違い／`stable` なのに sources が `review`／承認のある種類の `stable` に `verified` がない／テストの確認 ID が test-case にない／test-case の確認 ID がテストのコード（自動）か AC（手動）にない
- **厳しいモード**（`--strict`、リリース）：未実装・未記録も 0 に
- 承認待ちの間の「`stable` なのに sources が `review`」は正常（承認で消える）。`review` のまま push すると CI が落ちるので、承認のあとに push する。
- Windows の PowerShell では `npm run x -- --flag` のフラグが届かないことがある。`node scripts/check-docs.mjs --strict` で直接動かす。

## 8. 段階ごとに先に確かめておくこと（よく手戻りになるもの）

### 00〜02

- 仕様書に版と改訂履歴を持たせ、成果物の sources に版を書く。
- 同じサイトにほかのアプリも載るなら、保存のキー・キャッシュを分けるアプリ識別子を決める。
- PWA なら、更新の切り替え方（勝手に切り替えない・「更新」ボタン）と、起動に失敗したときの復旧を決める。
- README と、権利・クレジットの表記をいつ作るかを決める（リリースで作るなど）。
- 非機能要件（60 fps・入力の遅れなど）も、確かめ方（自動か手動か）まで書く。
- 数値の条件（点数・ボーナスなど）が、1 回の利用で届くかを、取れる幅を出して確かめる。

### 03 画面設計

- スマートフォンで、操作する指で大事なものが隠れないか。
- キーボードが出たとき・ノッチ・ホームバー・ホーム画面のアプリのステータスバー。
- アプリの名前がホーム画面で切れないか。
- **画面にアプリの版を出すかと、その場所**。
- 大きさの基準は、**E2E で使う端末の大きさ**も含めて確かめる（Playwright の「iPhone SE」は第 1 世代 320 × 568。基準が 375 × 667 なら `iPhone SE (3rd gen)`）。
- iPhone のタッチは CSS だけでは長押しの虫めがね・2 回タップの拡大が止まらない。操作する場所では `touchstart` の既定の動きと `gesturestart` を止めると決める。
- 黒い背景のフォームの部品（ラジオ・チェック）は、標準の見た目に頼らず CSS で描く。
- 大きな文字の日本語（見出しなど）は、狭い画面で折り返したときの区切りを見る。「ー」などが行の頭に来ないよう、CSS の `line-break: strict` にする。

### 04 詳細設計

- ロジックは DOM・時刻・乱数に触れない作り（状態と入力から次の状態を返す関数）にし、単体テストで確かめる。乱数は種を外から渡す。
- 中身を E2E から読めないもの（Canvas など）は、テスト用の入口（`?debug=1`、body の data 属性、状態の読み書き・停止・ステップ実行）を設計に入れる。
- 文字の入力欄を置く画面では、ページ全体のキー操作が入力欄で効かないようにする。
- 画像から絵を作るときは、設計の前に画像を点で読み取り、その並びを設計とテストの期待値にする。
- 同じ変化を 2 つ以上の部品が受け取り、受け取る順番で結果が変わるとき（例：音をオンにしたとき「確認音を鳴らす」と「BGM の監督に知らせる」）は、その順番を詳細設計に書く。書いていないと、作るときに偶然の順番になる（WS-0009 のふりかえり）。
- 「どこに出すか」（エラー・メッセージ・確認の置き場所）は、仕様書の文とテストケースに 1 つずつ突き合わせてから書く。画面設計から書き写すと、仕様書とずれることがある。

### 05 テスト

- 実機でしか分からない項目（実機のブラウザ・ホーム画面のアプリ・音・読み上げなど）を、手動のテストケースとして先に一覧にする。**その手順が実機でできるか**まで確かめる（ホーム画面のアプリは URL を変えられない、など）。
- E2E は CI と手元でフォントが違う。文字の幅に頼らない。収まりの判定は行の高さを決め打ちにして余裕を残す。
- 時間を進めるテストは、偽の時計を止めてから進める（Playwright：`install` → `pauseAt` → `runFor`）。`install` だけでは時計が自然に進み、数 ms ずれる。時間で変わる表示は、状態をそろえてから見るか操作の直後に見る。
- Playwright は `aria-disabled="true"` の要素を「押せるようになるまで」待つ。無効の項目を押しても何も起きないことを確かめるときは、`click({ force: true })`・`tap({ force: true })` で押す。
- Playwright の `framenavigated` は、URL の `#` 以降だけの変化（`history.replaceState` を含む）でも起きる。読み込み直しの回数を数えるときは、`#` 以降だけの変化を数えない。
- 「超えたら」「以内」などの境目は、偽の時計で、境目ちょうどと 1 つ先の両方を確かめる。偽の時計はちょうどの時刻のタイマーも動かすので、「超える」と「以上」の違いは境目ちょうどのときにだけ出る。
- CSS の値を `getComputedStyle` で確かめるときは、ブラウザが返す形で書く（例：`step-end` は `steps(1)` と返る）。
- メッセージの行の数をちょうどで確かめるテストは、折り返さない短い文の場面で作る。長い文は画面の幅で折り返し、欄に入る行の数が変わるので、「最大以下・最新の行が出る・欄の高さを超えない」で確かめる。
- E2E で保存を消して開き直すときは、いったん `about:blank` へ移ってから開く。`#` 以降だけが違う URL へは、読み込み直さずに移る（アプリが前の状態を持ったまま）。
- 新しいタブは、最初から空のページの分の履歴を持つ。「履歴が増えない」は 1 と比べず、置き換えの起きない URL をふつうに開いたときの `history.length` と比べる。
- 状態で操作を分けるときは、1 回読んで分けず、端末で分けるか状態が変わるのを待つ。
- 物を置く位置は、1 ステップの移動量ではなく境目（接する位置）から決める。画面を開く関数は、前の状態が残らない開き方にする。
- 画素を読む E2E は、倍率が変わっても同じ結果になる場所を選ぶ。新しく描く物が読む範囲にかからないか、先に grep する。
- テストを置き換えたら、すぐ check:docs で確認 ID のテストが消えていないかを見る。
- E2E で `setViewportSize` のあとに大きさ・位置を測るときは、`expect.poll` で落ち着くまで待つ。600px の境目をまたぐと画面を作り直し、その途中を測ると 0 になる（WS-0008 のふりかえり）。
- テストで確かめる値（保存のキー・記録など）を、そのテストの中で自分で書かない。アプリが何をしても通るテストになる（WS-0008 のふりかえり）。
- テストケースで別の確認の手順を借りるとき（「〇〇と同じ操作」）は、その場面で期待する結果が本当に起きるかを、仕様書の決まりに当てはめて確かめる（例：ボスを倒す場面では最後の演出はクリアで、ドロップではない。WS-0007 のふりかえり）。
- テストケースの準備に書く例の値（装備・敵・状態）が、ルールの決まり（段階で出るレアリティ・値の範囲など）を満たすかを確かめる。読み込みで直される値だと、画面の文字が例と変わる（WS-0006 のふりかえり）。
- アプリのファイルを止めたり差し替えたりする E2E（`page.route`）は、Service Worker を止めて動かす（`test.use({ serviceWorkers: 'block' })`）。Service Worker が保存したファイルを先に出すと、止めたつもりの読み込みが止まらない。
- 画面をまたぐ流れ（前の画面のメッセージを持ち込んで次の画面を開く：名前入力 → 宿屋、遭遇 → 戦闘、ボスの撃破 → クリアなど）は、テスト用の入口で場面を直接作らず、実際の操作で通すテストを 1 つは持つ。直接作る場面では、メッセージを出している途中の状態に当たらない（WS-0010 のふりかえり）。
- 検査の仕組み（CI・check:docs など）を変えたら、通る場合だけでなく、わざと誤りを入れて落ちる場合も確かめる手動の確認を入れる。飛ばす・分ける変更で、見逃すようになっていないかは、通る場合だけでは分からない（WS-0014 のふりかえり）。
- 偽の時計は、プログラムのタイマーを進めるが、画面の CSS のアニメーションは進めない。アニメーションが終わったかどうかは確かめられないので、長さ・回数を読んで確かめる。待ちの長さ（演出の長さなど）を変えたら、実時間で待つテスト（`expect.poll` の上限など）も探して直す（WS-0016 のふりかえり）。

### 06 作業計画

- 確認 ID を US の番号で機械的に TASK に割り当てない。PR の前に、**各確認 ID が、その TASK の時点でそろう機能（前の TASK までに作るもの）だけで書けるか** を 1 つずつ点検し、書けないものは機能がそろういちばん早い TASK に移す。あわせて、確認 ID の準備・手順が使う部品（テスト用の共通の操作・画面どうしのつなぎ）が、どれかの TASK の「やること」に入っているかを見る。
- 乱数を引く順が決まっている処理（例：勝利 → レベルアップの成長 → ドロップ）は、同じ TASK に入れる。ユーザーストーリーの区切りで分けると、先の TASK で前倒しして作ることになり、設計書を何度も直す。
- 仕様書のファイル構成（README・設定ファイルなど）の各ファイルが、どれかの TASK の「やること」に入っているかを確かめる。入っていないファイルは、リリースの点検まで誰も作らない（リリース 1.0.0 のふりかえり：README）。
- CI・公開の設定を変える WS では、マージのあとに確かめるための PR（文書だけの PR など）を、はじめから作業計画に入れる。新しい設定は本流に入ってから効くので、実装の PR だけでは確かめきれない（WS-0014 のふりかえり）。

### 07 実装

- PR の前に、手元で verify と E2E を通す（E2E が build したものを動かすなら、先に build）。
- 単体テストでは、置いた位置が前提を満たすこと（重なる・重ならない）を先に確かめてから本題を確かめる。同じ値で決まる規則は、値をちょうど与えて確かめる。
- テスト用の入口で場面を作るときは、狙う物以外を消して前提を先に確かめる。結果（点数など）は決め打ちせず状態から読む。
- 1 秒あたりの値（fps など）は、実際にたった時間で割って出す。
- 新しい絵や画面は、PR の前にスクリーンショット（PC と一番小さいスマートフォン）で形を見る。
- 部品を作る TASK と、それを使う画面の TASK が分かれているときは、使う TASK の E2E で、部品の基本の操作（2 行目以降を押す・キーで動かす・無効の項目を選ぶ）を最初に確かめる。部品だけの TASK では、押して確かめる画面がない。
- 表示を更新するときは、押される要素（メニューの行・ボタン）を作り直さず、中身（文字・class・属性）だけを書き替える。押し始めと押し終わりで要素が替わると、クリック・タップが届かない。
- 調べ物・撮影用の一時ファイルは、プロジェクトの外の作業用の一時フォルダに置く。プロジェクトの中に置くと、コミットに混ざるおそれがあり、設定によっては消せない。撮影用の E2E は、一時フォルダに Playwright の設定ファイル（`testDir: '.'`、`webServer.cwd` にプロジェクト）とテストを置き、`NODE_PATH` にプロジェクトの `node_modules` を指して動かす（設定ファイルは `@playwright/test` を import しない）。
- テストの名前は、確認 ID のすぐ後ろに空白を入れる（`test('TC-0000-00 …')`）。編集の道具に渡す文を空白で終わらせない（末尾の空白が落ちて確認 ID が文とつながり、check:docs が数えなくなる）。
- スクロールする部品（`overflow: auto`）の中に `position: absolute` の要素（読み上げ用の隠し文など）を置くときは、スクロールする要素を `position: relative` にする。しないと枠で切られず、ページが縦に伸びる（WS-0006 のふりかえり）。
- 一覧・スクロールのある画面を作ったら、375 × 667・414 × 715・1280 × 800・1366 × 657 の 4 つで、はみ出し（`scrollHeight − innerHeight` と横の同じ値）を測る。項目の多い場面（所持品 50 個など）でも測る。写真を見るだけでは、数 px のはみ出しや項目が多いときのはみ出しを見落とす（WS-0006 のふりかえり）。
- 仕様書に全文があるコードは、行の範囲で切り出して写し（手で打ち直さない）、すぐに型の検査と lint を動かす。仕様書のコードは、このリポジトリの検査の設定で確かめていないことがある。直したところは AC に書く（WS-0009 のふりかえり）。
- E2E で、開き直す場面づくり（`startAt` など）のあとにイベントの記録を見るときは、その場面のイベントが出るまで待ってから記録を空にし、そこから先だけを見る。開いたときのタイトルなどのイベントが先に入る（WS-0009 のふりかえり）。
- 手元の E2E が急に時間切れになったら、失敗したときの画面の記録（`test-results/**/error-context.md`）を見て、このアプリが出ているかを確かめる。別のアプリが出ていたら、同じポート（4173）を別のアプリが使っている（手元では、動いているアプリをそのまま使う設定のため）。止まってから動かし直す（WS-0008 のふりかえり）。
- E2E で、要素があるかどうかを見るときは `page.evaluate` の `querySelector` か `locator.count()` を使う。`locator.evaluate` は要素が出るまで待つので、ループの中で使うと 1 回目で時間切れになる（WS-0007 のふりかえり）。
- `addInitScript` で仕込んだ記録（イベントの記録など）は、ページを開き直すたびに空になる。場面を作り直す（開き直す）テストでは、場面ごとに記録を見る（WS-0007 のふりかえり）。
- 全角スペースは、ソースのテンプレート文字列（`` ` `` で囲む文字列）と正規表現に直接書かない（lint の `no-irregular-whitespace` が止める）。ソースでは `String.fromCharCode(0x3000)`、テストの正規表現では `\s` を使う。
- 手元では通る、画面の大きさ・位置を測るテストが CI だけで落ちたら、まず、アプリが描いたあとに直す処理（次のコマ・タイマーで高さを合わせるなど）の前を測っていないかを、直す前と後を 1 つのテストで測って確かめる。CI は手元より遅く、直す前を測ることがある。測る前に 2 コマ待つ（`requestAnimationFrame` を 2 回）（WS-0010 のふりかえり）。
- 1 つの画面で、フォーカス・メニューを止める／解くなどの扱いを直したら、同じ作りのほかの画面にも同じ直しが要るかを、その場で確かめる。同じ抜けが別の画面に残る（WS-0010 のふりかえり）。
- 文書の書き替えは、編集の道具（Edit）を使う。PowerShell で一括の置き換えをするときは、組を 1 つずつ引数で渡し（配列で 1 組だけ渡すと 1 文字ずつに分かれる）、「見つからなければ止める」を入れ、関数の名前を既存の別名（`R`・`h`・`r` など）と重ねない。書き替えたら `git diff` で全部を見てからコミットする。一括の置き換えは、壊れても気づきにくい（WS-0011 のふりかえり）。
- 値（大きさ・MD5 など）を変える実装では、直す前に、古い値でテスト・ソース・検査のスクリプトを探し、直す場所を全部挙げてから直す。作業計画に挙げた場所だけを直すと、ほかのテストが同じ値を見ていても気づかない（WS-0012 のふりかえり）。
- コミットの前に `git status` で入るファイルを見て、自分が直したファイルだけを入れる（`git add docs` のようにフォルダごとに入れない）。作業の途中に、オーナーがファイルを置くことがある（WS-0012 のふりかえり）。
- 履歴を書き換えるコマンド（`--amend`・`reset`・`rebase` など）や、前のコマンドの成功が前提のコマンドは、1 行に続けて並べない。1 つずつ動かして結果を見てから次へ進む。前のコマンドが失敗しても次のコマンドが動き、別のコミットを書き換える（WS-0014 のふりかえり：`git revert` の失敗のあと `--amend` が誤りのコミットを書き換えた）。
- マージ（公開）のあと pages が失敗したら、記録（`gh run view`）で、組み立て（build）と載せ替え（deploy）のどちらで失敗したかを見る。載せ替えだけの失敗（「Deployment failed, try again later.」など）なら、失敗したジョブだけを再実行し、公開中のページのプログラムを読んで、新しい版にしかない文字（古い版にない文字）が入っているかで確かめる（WS-0016 のふりかえり）。
- 撮影や確かめのために動かしたサーバー（`vite preview` など）は、使い終わったら止める。次に使う前に、同じ番号のサーバーが残っていないか、残っていれば最新の組み立て結果を出しているか（ファイルの MD5 など）を確かめる。残ったサーバーがあると、新しいサーバーは起動に失敗し、E2E も古い結果を使うことがある（WS-0017 のふりかえり）。

## 9. ふりかえり（YWT）

置き場所：`doc/retrospectives/`（ID・承認なし、check:docs の対象外）。Claude Code が案を書き、オーナーが見て足す。

| いつ | ファイル |
| :--- | :--- |
| WS の終わり | `ws-<番号>.md` |
| リリース | `release.md` |
| 完了 | `summary.md` |

```markdown
# WS-<番号> のふりかえり（<日付>）

対象：<PREFIX>-WS-<番号>（TASK-<番号>〜<番号>、PR #<番号>〜#<番号>）

## Y（やったこと）
- 前回の T を守れたか（最初に確かめる）
- 終えた TASK と、作った・直したもの
## W（わかったこと）
- うまくいったこと、つまずいたこと（手戻り・CI の失敗・実機で見つかった問題）と原因
## T（つぎにやること）
- 次に変えること。この文書（8 章など）のどこに足すかも書く
```

- 1 項目 1〜2 行、全体で 1 画面ほど。
- エンジニアでないオーナーが読むので、**最初に言葉の表**（WS・TASK・PR・確認 ID・CI など、本文に出る専門の言葉の言い換え）を置く。W のつまずきは「何が起きたか・なぜ・どうしたか」に分けて書き、T には理由を添える（1.1 の解説の付け方）。このときは 1 画面を超えてよい。
- T は、次の WS を始める前にこの文書に反映する。
- `summary.md`：Y（全体の数と WS ごとの表）、W（くり返し効いたこと・くり返し出たつまずきとどう直したか）、T（次のプロジェクトで最初から入れること）。
