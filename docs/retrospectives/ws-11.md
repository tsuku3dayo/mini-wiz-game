ふりかえりは YWT の形で書く：**Y**＝やったこと、**W**＝わかったこと、**T**＝つぎにやること。

## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| 変更の依頼 | 完成したあとに仕様を変えるときの手続き。依頼を記録し、仕様書の版を上げ、影響する文書を直してから作る |
| WS（ワークストリーム）・TASK | 作る作業のまとまりと、その中のひとつひとつの作業。1 つの TASK を 1 つの PR にする |
| AC（実施記録） | TASK を実際にやって確かめた結果の記録。番号は TASK と同じにする決まり |
| PR（プルリクエスト） | 変更を本流（main）に入れてよいか、確かめてもらうための申請。オーナーがマージ（取り込み）すると公開される |
| PowerShell | Windows で命令を打ち込んで動かす道具。Claude Code はこれで文書の一括の書き替えもしていた |
| 別名 | PowerShell が、短い名前に前から割り当てている命令。同じ名前を自分で使うと、思わぬ命令が動く |

## W（わかったこと）

- **PowerShell の一括の置き換えで、文書を 5 つ壊した（2026-11-05。`git checkout` で元に戻した）。**
  - 何が起きたか：置き換える組（前の文字と後の文字）を配列で渡したとき、組が 1 つだけだと、PowerShell が配列を 1 文字ずつに分けてしまい、思わぬ所が置き換わった。
  - もう 1 つ：置き換えの関数に `R` という名前を付けたら、PowerShell が前から持っている別名（「前の命令をもう一度動かす」）とぶつかった。
  - 今日も、複数行の置き換えが改行の形（Windows の CRLF と LF）の違いで見つからなかった。このときは「見つからなければ止める」を入れていたので、ファイルは書き替わらずに済み、編集の道具（Edit）でやり直した。
  - どちらも、手で打つ編集の道具を使えば起きなかった。一括の置き換えは便利だが、壊れても気づきにくい。
- **TASK と AC の番号が、1 つずれた。**
  - 決まりは「AC の番号は TASK と同じ」。ところが、リリースの記録に TASK のない AC-0024 を使っていたので、次の TASK を 0024 にすると AC と番号がそろわない。今回は TASK-0024 を欠番にして TASK-0025・AC-0025 にした（依頼 §2.2 の 8 でオーナーに確かめた）。
  - リリース・完了のように TASK のない記録の番号の付け方を、先に決めていなかった。
- **実機の確認を 3 つにしぼって頼んだので、テストケースの手順の一部は頼んでいなかった。**
  - TC-0002-07 は「追加したアプリからダンジョンまで遊べる」まで、TC-0006-13 は「セーブのある状態でも見る」までが手順だが、案内では名前と画像だけを挙げた。変えたのが名前と画像だけなので困りはしないが、AC の「確認できなかったこと」に書くことになった。
  - しぼるなら、案内を出す時点で「手順のうち、ここは今回見ない」と決めてオーナーに伝えるほうがよかった。
- **先に制約を調べて伝えたので、画像は 1 回で決まった。** 大きさ・形式・容量の目安を先に渡したことで、作り直しなしで仕様書に入れられた。

## T（つぎにやること）

- **文書の書き替えは、編集の道具（Edit）を使う。PowerShell で一括の置き換えをするときは、組を 1 つずつ引数で渡し、「見つからなければ止める」を入れ、関数の名前は既存の別名（`R`・`h`・`r` など）と重ねない。書き替えたら `git diff` で全部を見てからコミットする。** 一括の置き換えは、壊れても気づきにくいため。→ 手順書 §8「07 実装」に足す。
- **TASK のない記録（リリース・完了）に AC の番号を使ったら、次の TASK はその番号を飛ばし、TASK と AC の番号をそろえる。** 番号のずれを、その場の相談で決めないため。→ 手順書 §3.3 に足す。
- **実機の確認を、テストケースの手順の一部にしぼって頼むときは、しぼった理由と「今回は見ない手順」を案内に書き、AC の「確認できなかったこと」にも書く。** 頼んでいない手順が、あとから見つかってあわてないため。→ 手順書 §4.4 に足す。
