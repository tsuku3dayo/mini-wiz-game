## W（わかったこと）

- **仕様書に見本の値があると、作ったものが合っているかをすぐ確かめられた。**
  - 迷路の作り方は手順が長く、乱数を引く順が 1 つずれても別の迷路になる。仕様書の見本の値（SHA-256 の先頭 16 桁）と一致したので、順番まで仕様どおりだと分かった。
- **承認済みの記録の「版の表記」だけを直す場面が、何度も来た。**
  - 何が起きたか：設計書の版を上げるたびに、承認済みの実施記録（AC）の「根拠にした版」の表記を直す必要があった。WS-0002 のふりかえりの反映（PR #37）と TASK-0008 で、2 回続けてオーナーに聞いた。
  - どうしたか：「中身を変えず、版の表記だけなら承認済みのまま直してよい」という決まりをオーナーに了承してもらい、CLAUDE.md に書いた。
- **「300ms を超えたら」の境目を、ちょうど 300ms で出していた。**
  - 何が起きたか：応答待ちの ▼ を出すまでの時間を「300ms ちょうど」にしていた。前の WS のテストは 299ms と 301ms で確かめていたので、ずれに気づかなかった。今回のテスト（TC-0011-08）は 300ms と 301ms で確かめたので、気づいた。
  - なぜ起きたか：偽の時計は、ちょうどその時刻のタイマーも動かす。「超えたら」と「以上」の違いが、境目ちょうどのときにだけ出る。
  - どうしたか：1ms 足して待ち、仕様どおり「超えたら」にした。
- **E2E のテストの書き方で、3 か所つまずいた。** どれもアプリの不具合ではなかった。
  - 外周以外に壁のない地図の真ん中では、1 歩進んでも前方の見え方が変わらない。見え方が変わる、壁の近くの位置で確かめるようにした。
  - 実績の項目名 `bossKills` に「boss」が含まれていて、「ボスの位置を画面に渡していない」の確かめに引っかかった。項目名そのもの（`"boss":`）で探すようにした。
  - CSS の `step-end` は、ブラウザに読むと `steps(1)` と返ってくる。期待する値をそれに合わせた。
- **全角スペースを、ソースの文字列に直接書いてまた止められた。** 書き方のチェック（lint）が止めるのは、テンプレート文字列（`` ` `` で囲む文字列）と正規表現の中の全角スペース。前の WS でも同じことが起きた。
- **公開版で、途中までしか遊べない場面ができた。**
  - 何が起きたか：戦闘の画面は TASK-0011 で作る計画なので、いまの公開版では、歩いて敵に出会うと画面が空になる。
  - どうしたか：PR とオーナーへの報告に、その場面と抜け方（「つづきから」）を書いた。

## T（つぎにやること）

- **「超えたら」「以内」などの境目は、偽の時計で境目ちょうどと 1 つ先の両方を確かめる。** 「超える」と「以上」の違いは、境目ちょうどのときにだけ出るため。→ 手順書 §8「05 テスト」に足す。
- **CSS の値を読んで確かめるときは、ブラウザが返す形で書く（例：`step-end` は `steps(1)`）。** 書いた形と読める形が違うことがあるため。→ 手順書 §8「05 テスト」に足す。
- **全角スペースは、ソースのテンプレート文字列と正規表現に直接書かない。** ソースでは `String.fromCharCode(0x3000)`、テストの正規表現では `\s` を使う。書き方のチェックが止めるため。→ 手順書 §8「07 実装」に足す。
- **撮影用のテストは、プロジェクトの外の一時フォルダに設定ファイルと一緒に置き、`NODE_PATH` にプロジェクトの `node_modules` を指して動かす。** 今回うまくいったやり方を残すため。→ 手順書 §8「07 実装」の一時ファイルの行に足す。
- **公開版に、途中までしか遊べない場面が残るときは、PR とオーナーへの報告に、その場面と抜け方を書く。** 遊んだ人が困らないようにするため。→ 手順書 §4.3「07 実装」に足す。
