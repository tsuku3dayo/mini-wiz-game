# WS-0018 のふりかえり（2026-11-11）

対象：MWIZ-WS-0018 クレジット画面（変更の依頼 v1.12・v1.13。TASK-0034、PR #108〜#111）

オーナーの承認：（承認待ち）

ふりかえりは YWT の形で書く：**Y**＝やったこと、**W**＝わかったこと、**T**＝つぎにやること。

## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| WS・TASK | 作業のまとまり（WS）と、その中の 1 つ 1 つの作業（TASK） |
| PR | 変更を本流に入れてよいか確かめてもらう申請 |
| E2E | 本物のブラウザを自動で動かして、画面を通して確かめるテスト |
| はみ出し | 画面の高さに中身が収まらず、縦にスクロールが出ること |
| エラーの枠 | 保存に失敗したときなどに、タイトルに出る「続けられません」の知らせの枠 |
| BOM | 文字のファイルの先頭に付くことがある、目に見えない 3 バイトの印。コミットの題に入ると、題の頭に見えない文字が混ざる |
| GUI-0002 | 承認済みの画面設計（タイトル画面など）の文書 |

## Y（やったこと）

- 前回の T のうち「素材を置く前に形式を調べる」は、オーナーの例の画像（`credits-example.png`）を並び方の見本として使い、ゲームには置かなかったので当てはまらなかった。「撮影のサーバーは使い終わったら止める」は守れた。
- 変更の依頼 v1.12（タイトルの「おと」の下に「クレジット」を足し、役割と名前の 6 組を並べた画面を開けるようにする）→ 仕様書 v1.12 と PB-0001・EP-0002・US-0006・US-0039・GUI-0002 の再承認 → 設計・テスト・作業計画 → 実装 → 公開まで、同じ日に進めた（PR #108・#109・#111）。
- 実装の途中で、メニューが 4 行になったためエラーの枠が出るとタイトルがはみ出すと分かり、変更の依頼 v1.13（高さ 680 以下で上下の余白を 32 → 16）を出して承認を受けてから作った（PR #110）。
- 実機の確認は、iPhone で OK（見え方・戻れた・曲が途切れない）。PC はまだ結果をいただいていない（E2E の PC の大きさでは確かめてある）。

## W（わかったこと）

- **高さの見込みを、測らずに引き算で出して外れた。**
  - 何が起きたか：v1.12 の依頼書で「エラーの枠が出ても約 6px 余るので収まる」と書いたが、作ってみると 375 × 667 で 22px、1366 × 657 で 9px はみ出した。
  - なぜ：エラーの枠のない画面の余りから、枠の高さ（102px）を引いただけで、枠のまわりのすき間（16px など）を数えていなかった。
  - どうしたか：v1.13 の変更の依頼を出し、2 つの案を手元で実際に CSS を当てて測ってから選んでもらった。最初から測っていれば、v1.12 の中で決められ、依頼が 1 つで済んだ。
- **承認済みの画面設計（GUI-0002）を、実装の途中で変えることになった。**
  - 何が起きたか：v1.12 で承認を受けた GUI-0002 v1.2 を、同じ日に v1.3 に上げて再承認を受けた。
  - なぜ：上の見込み違いのため。画面に物を足すときに、「いちばん狭い画面」「いちばん物が多い場面（エラーの枠あり）」で収まるかを、承認の前に測っていなかった。
  - どうしたか：決まりどおり変更の依頼 → 再承認の順に進めたので、記録は残った。ただ、オーナーの承認の手間が 1 回増えた。
- **コミットの題に BOM が入った（576e90c）。**
  - 何が起きたか：コミットの題の頭に、見えない文字が混ざった。
  - なぜ：前に BOM 付きで作ったメッセージのファイルを上書きして使い回したため、BOM が残った。
  - どうしたか：履歴は書き換えずに残し、メッセージのファイルは毎回新しい名前で作り、先頭の 3 バイトを確かめてからコミットするようにした。
- **うまくいったこと：はみ出しは E2E（TC-0040-09・TC-0035-12）が公開の前に見つけた。** 前の WS で入れた「4 つの大きさではみ出しを測る」決まりが効いた。

## T（つぎにやること）

- **画面に物を足す変更の依頼では、承認を求める前に、手元で CSS を当てて、いちばん物が多い場面（エラーの枠・項目の多い一覧など）のはみ出しを 4 つの大きさで測り、その値を依頼書に書く。引き算の見込みで書かない。** 理由：見込みが外れると、承認済みの文書を同じ日に再承認することになる。→ 手順書 §6（変更の依頼）と §8「03 画面設計」に足す。
- **コミット・PR の本文のファイルは、毎回新しい名前で作り、先頭が BOM（EF BB BF）でないか確かめてから使う。** 理由：BOM 付きのファイルを上書きしても BOM が残り、題に見えない文字が入る。→ 手順書 §8「07 実装」に足す。
