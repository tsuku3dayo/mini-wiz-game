# 全体のふりかえり（2026-11-05）

対象：mini-wiz-game「WIZ ～死霊術師の迷宮～」の開発の全体（WS-0001〜0010、リリース 1.0.0）。WS ごとの詳しいふりかえりは `ws-01.md`〜`ws-10.md`・`release.md` にある。

ふりかえりは YWT の形で書く：**Y**＝やったこと、**W**＝わかったこと、**T**＝つぎにやること。

## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| WS（ワークストリーム） | 作る作業のまとまり。全部で 10 個 |
| TASK | WS の中のひとつひとつの作業。1 つの TASK を 1 つの PR にした。全部で 23 個 |
| PR（プルリクエスト） | 変更を本流（main）に入れてよいか、確かめてもらうための申請。オーナーがマージ（取り込み）すると公開される |
| 確認 ID | 「何を確かめるか」1 つごとに付けた番号。全部で 323 個（自動 306・手動 17） |
| AC（実施記録） | TASK ごとに「実際にやって確かめた結果」を書いた文書 |
| 手順書 | 開発の進め方を書いた `docs/SDD-PROCESS_v3.md`。ふりかえりの T をここに書き足していった |
| CI | GitHub の上で、PR ごとに自動でテストを動かすしくみ |

## 全体の W（わかったこと）

- **ふりかえりの T を、次の WS の前に手順書へ入れる流れは、よく効いた。**
  - 同じ種類のつまずき（確認 ID の数え漏れ、境目の時間、実機の手順を渡す時機など）は、手順書に入れたあとの WS では、ほとんど繰り返さなかった。
  - ただ、手順書に書いたことでも、作業のときに読み直さないと守れない。WS-0010 で持ち物の値の決まり（WS-0006 の T）でまたつまずき、完了の作業中に、コマンドのリスク評価の段階（WS-0008 の T。GitHub に送る・PR を作る・ブランチを消すは「高」）を、WS-0010 からずっと「中」と表示していたことに気づいた。
- **作業計画（06）の点検の漏れが、あとの WS で何度も手戻りになった。**
  - まだ書けないテストの割り当て（WS-0001）、道具の機能（WS-0005）、乱数の順による前倒し（WS-0004）、README（リリース）。どれも「その TASK の時点で何がそろうか」「仕様書の全部の項目が誰かの TASK に入っているか」を、計画のときに 1 つずつ見ていなかったことから来た。
- **仕様書に、見本の値・全文のコード・MD5 があると、作ったものの正しさをすぐ確かめられた。** 迷路のハッシュ、BGM の曲データ、敵の絵の MD5 がそうだった。
- **実機の確認は、手順・「見ること」・返事のひな形・行けない場面の案内を、公開の前にまとめて渡すと、1 回で済んだ。** 渡し方が固まるまで（WS-0006 まで）は、見られない確認が出た。
- **テストの道具（Playwright・偽の時計・Service Worker・Windows の PowerShell）の決まりで、毎回のようにつまずいた。** どれもアプリの不具合ではなく、手順書 §8 に書きためた決まりが、そのまま次の WS の助けになった。

## 全体の T（つぎのプロジェクトでやること）

- **作業計画を作るとき、仕様書の全部の項目（受け入れ基準・ファイル構成・テスト用の道具）が、どれかの TASK の「やること」と確認 ID に入っているかを、表にして 1 つずつ確かめる。** 計画の漏れが、いちばん多くの手戻りを生んだため。
- **作業を始めるとき（セッションの最初・WS の最初）に、手順書と記憶の決まり（リスク評価・コミットの書き方など）を読み直す。** 書いてあっても、読み直さないと守れなかったため。
- **ふりかえりの T を、次の WS の前に手順書へ入れる流れは続ける。**
