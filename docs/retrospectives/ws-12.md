# WS-0012 のふりかえり（2026-11-06）

対象：MWIZ-WS-0012 タイトル画像と敵の絵の差し替え（変更の依頼 v1.4・v1.5・v1.6。TASK-0026・0027・0028、PR #77〜#80・#82〜#84・#86・#87）

ふりかえりは YWT の形で書く：**Y**＝やったこと、**W**＝わかったこと、**T**＝つぎにやること。

## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| 変更の依頼 | 完成したあとに仕様を変えるときの手続き。依頼を記録し、仕様書の版を上げ、影響する文書を直してから作る |
| MD5 | ファイルの中身から計算する短い文字列。中身が 1 バイトでも違えば別の値になるので、「同じファイルか」を確かめるのに使う |

## Y（やったこと）

- 前回（WS-0011）の T：3 つとも手順書 SDD-PROCESS に入れてあり、今回は次のように効いた。
  - 文書の書き替えは編集の道具を使う、一括で置き換えるときは「見つからなければ止める」：組の JSON を渡す小さなプログラム（1 か所ずつ、見つからなければ何も書かずに止める）を作って使った。書き替える前に止まったのは 2 回（PowerShell の置き換えで、文字の中の `${p}` が PowerShell に置き換えられて見つからなかった。同じ文が 2 か所あった）。どちらも書き替える前に止まり、文書は 1 つも壊れなかった。
  - 確認をしぼるときは、理由と「今回は見ない手順」を案内に書く：タイトル画面のセーブのある状態を見ない理由を、案内と AC に書いた。
- オーナーの絵の差し替えを 3 回続けて受けた。
  - **v1.4**：タイトル画像と、128×128 の敵の絵（画面では 2 倍の 256px）。タイトル画像は実機で OK だった。
  - **v1.5**：敵の絵を同じ絵柄の 256×256 に（128×128 の絵は、実機で見る前に替えた）。実機で OK だった。
  - **v1.6**：敵の絵を v3 に。5 枚に半透明の点があったので、決まりを「半透明の点があってもよい」に改めた。実機（iPhone・PC）で 6 体とも OK だった。
- どの依頼も、依頼の記録 → 仕様書と承認済みの文書の再承認 → 設計・テスト・作業計画 → 実装 → 実機の確認、の順で進めた。依頼ごとに PR を 3 つ（仕様・計画・実装）作った。
- 仕様書のもとになる文書の版の表記は、毎回 100 ほどの文書で直した。文書の頭の欄の中だけを、1 か所ずつ置き換えるプログラムで行った。

## W（わかったこと）

- **テストの直し漏れが 1 か所あった（TASK-0026）。**
  - 何が起きたか：敵の絵の大きさを 256 から 128 に変えたとき、作業計画に挙げたテストだけを直した。通信なしで遊べるかを確かめる E2E（`e2e/pwa.spec.ts`）も絵の大きさ 256 を見ていて、6 件落ちた。
  - どうしたか：`naturalWidth` と `256` をテストとソースで探し直し、ほかにないことを確かめてから直した。次の TASK-0027・0028 では、直す前に古い値（`128`、古い MD5）を探して直す場所を全部挙げてから直したので、1 回目で全部通った。
  - 値を変えるときは「値そのもので探す」と手順書 §6 に書いてあったが、依頼の影響の一覧を書くときだけでなく、実装の前にも探すべきだった。
- **まとめてコミットしたとき、オーナーのファイルを巻き込んだ。**
  - 何が起きたか：`git add docs` で文書をまとめてコミットしたら、作業の途中にオーナーが置いた `docs/SDD-PROCESS_v4.md` も入った。
  - どうしたか：GitHub に送る前に気づき、コミットからだけ外した（ファイルはそのまま）。そのあとは、コミットの前に `git status` で入るファイルを見て、フォルダごとではなく、直したファイルだけを入れた。
- **PR の番号を先に決め打ちして、ずれた。**
  - 何が起きたか：依頼書の「結果」の欄に、まだ作っていない PR の番号（#81）を書いた。その間にオーナーが別の PR を出していたので、実際は #82 になった。直すときに、積んだ枝の上で同じ表がぶつかり、付け替えのやり直しが要った。
  - どうしたか：そのあとは、PR を作ってから、出てきた番号を書いて送るようにした（#84・#86・#87）。#85 は Dependabot の PR で、このやり方でずれずに済んだ。
- **積んだ枝で先に作業しておくと、オーナーの待ち時間が短くなった。** 仕様の PR の自動テストを待つあいだに、計画と実装を手元で済ませた。ただし、前の PR を直すと上の枝も付け替えが要る（上の PR 番号の件）。
- **半透明の点は、規格を数えるプログラムで見つけた。** 見た目では分からず、決まりの「半透明の点なし」との食い違いは、点の数を数えて初めて分かった。前に同じことがあった記録（付録 A.5 の 9）が、決めるときの手がかりになった。
- **実機の確認の返事に、見た敵の名前がなかった（v2）。** 「確認しました」だけでは、どの敵を見たか・どの絵の結果かが分からず、次の質問で確かめた。v3 の案内では、名前を書く欄があることを強めに伝え、「全部」と返事をもらえた。

## T（つぎにやること）

- **値（大きさ・MD5 など）を変える実装では、直す前に、古い値でテスト・ソース・検査のスクリプトを探し、直す場所を全部挙げてから直す。** 作業計画に挙げた場所だけを直すと、ほかのテストが同じ値を見ていても気づかないため。→ 手順書 §8「07 実装」に足す。
- **コミットの前に `git status` で入るファイルを見て、自分が直したファイルだけを入れる（フォルダごとに入れない）。** 作業の途中に、オーナーがファイルを置くことがあるため。→ 手順書 §8「07 実装」に足す。
- **依頼書などに PR の番号を書くのは、PR を作ってから。** 番号は、ほかの人の PR や Dependabot の PR で先に使われることがあるため。→ 手順書 §6 に足す。
- **実機の確認の返事のひな形には、どの絵・どの版を見たかが分かる欄（見た敵の名前など）を付け、空いていたら聞き返す。** まとめた返事だけでは、AC にどの結果かを書けないため。→ 手順書 §4.4 に足す。
