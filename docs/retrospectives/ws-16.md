## W（わかったこと）

- **試聴ページで聴いて選ぶ流れは、音の仕様を決めるのに効いた。** 文字の説明では決められない「聞こえ方」を、オーナーが実際に聴いて決められた。選ばなかった案も残しておいたので、v1.10 で「いまのレベルアップの音を遭遇に使う」「レアの案をレベルアップに使う」という組み替えもできた。
- **実機の確認を WS の終わりにまとめたら、そのあいだに次の変更が入り、確認が 2 回引き継がれた。** v1.7 の効果音の確認は、v1.9 → v1.10 と送られ、記録 AC-0029 が 4 日 draft のままだった。結果として 1 回で済んだが、引き継ぎの記入が 3 つの記録と 2 つの依頼にまたがり、手間が増えた。
- **承認済みの US の受け入れ条件を途中に足すと、テストケースの「条件」の番号がずれる。** US-0032 の 8 番目に足したので、TC-0032 の 8 番以降の番号を全部直した。
- **偽の時計は、画面の CSS のアニメーションを進めない。** 新しいテスト（TC-0031-12）で「1200ms 進めたらアニメーションが終わっている」を確かめようとして失敗した。アニメーションの長さを読む形に直した。演出を延ばすと、実時間で待つテスト（TC-0036-01）の待ちの上限も超えた。
- **版を上げた文書の版の表記は、承認済みの記録（AC）の sources も直さないと、文書のチェックがエラーになる。** 1 回目は 59 件のエラーになり、表記だけを直すプログラムで直した。
- **同じ失敗を繰り返した。**
  - 自分が作った一時ファイル（`.rej`）の削除を「リスク：中」と表示して、3 回目の拒否を受けた（決まりでは削除は「高」）。消さずに作業用フォルダへ移した。
  - PowerShell では `npm run x -- --flag` のフラグが届かないことを、撮影用のサーバーを動かすときにまた踏んだ（メモには書いてあった）。
- **推しの案と違う案が選ばれたとき、影響を考え直す必要があった。** v1.10 は案 B（演出の長さは変えない）をおすすめしたが、オーナーは案 A を選んだ。案 A では、再承認が要る US が US-0034 から US-0031 に変わり、ボス出現の文字が長く残る見た目の変化も出た。選ばれたあとに影響の一覧を作り直し、見た目の変化も依頼に書き足した。

## T（つぎにやること）

- **公開したら、その WS の実機の確認をすぐ案内し、次の変更の依頼を始める前に結果をもらう。待っている確認があるのに新しい依頼を受けるときは、依頼書に「待っている確認をどう引き継ぐか」を書いて、オーナーに決めてもらう。** 確認が何度も送られ、記録が長く draft のままになるのを防ぐため。→ 手順書 §6（途中で仕様を変えるとき）に足す。
- **承認済みの US に受け入れ条件を足すときは、末尾に足す。** 途中に足すとテストケースの条件の番号が全部ずれるため。→ 手順書 §6 に足す。
- **E2E で偽の時計を使うとき、CSS のアニメーションの進み（終わったかどうか）は確かめられない。長さ・回数を読んで確かめる。待ちの長さを変えたら、実時間で待つテストの上限も探す。** → 手順書 §8「05 テスト」に足す。
- **ファイルの削除（Remove-Item など）は、自分が作った一時ファイルでも「リスク：高」と表示する。消さずに済むなら作業用フォルダへ移す。** → 手順書 §1（リスクの表示）に足す。
- **pages（公開）が失敗したら、組み立て・テストと載せ替えのどちらで失敗したかを記録で見る。載せ替えだけなら、失敗したジョブだけを再実行し、公開中のプログラムを読んで新しい版になったかを確かめる。** → 手順書 §8「07 実装」（マージ＝公開）に足す。
