## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| 透過・RGBA | 画像の点ごとに「透明さ」を持つ形式。持たない形式は RGB |
| 外側から続く（塗りつぶし） | 絵の 4 辺から、となりどうしでつながっている同じ色の点をたどること。画像ソフトの「塗りつぶし」と同じ考え方 |
| MD5 | ファイルの中身から作る短い指紋。1 バイトでも違えば変わるので、同じファイルかを確かめるのに使う |
| EXIF | 写真や画像に入る説明の情報（撮った機械・ソフト・日時など） |

## Y（やったこと）

- オーナーの依頼「敵の絵を v4 に差し替えて」を受け、まずファイルの形式を調べた。v4 は**背景が真っ黒で透明がない**（RGB）と分かった。今の決まり（背景透過）に合わず、そのまま置くと黒い四角が見える。
- 画面の背景色の上に v4 を並べた見本と、外側の黒だけを透明にした試しの見本を作り、オーナーに見比べて選んでもらった（外側の黒を透明にする、に決まった）。
- 加工を、Node.js の標準の機能だけで動く小さなプログラムにした。2 回動かして同じ結果（MD5）になること、別の方法（Windows の画像の機能）で作った結果と点ごとに同じことを確かめてから、仕様書に手順と MD5 を書いた。
- 公開リポジトリに置くファイルなので、v4 に入っていた説明の情報（EXIF）の中身を確かめた（画像ソフトの名前と画像の番号だけで、個人の情報はなかった）。加工した絵には残らない。
- 変更の依頼 → 仕様書 v1.11 と PB-0001・EP-0008 の再承認 → テスト・計画 → 実装 → 公開 → 実機の確認（iPhone・PC で OK）まで、同じ日に進めた。前回のふりかえりの T どおり、公開したらすぐ実機の確認を案内した。

## W（わかったこと）

- **渡された素材は、置く前に形式（透明の有無・色の種類・入っている情報）を調べると、決まりとの食い違いを先に見つけられる。** 名前を付け替えて置くだけの前回までのやり方だと、黒い四角が画面に出てから気づくところだった。
- **決めてもらうときは、文字の説明より、見本の画像を並べたほうが早い。** 「黒い四角が見える」「透明にするとなじむ」を見本で示したので、1 回の質問で決まった。
- **加工した素材は、手順を再現できる形（プログラム・入力・期待する MD5）で残すと、あとで確かめられる。** ただし、圧縮の部品の版が違うと MD5 が変わりうるので、そのときの直し方も仕様書に書いた。
- **「外側から続く黒だけ」を透明にすると、絵に囲まれた背景のすき間は黒のまま残る。** 撮影で気づき、実機で見てもらって問題なしになった。見本の段階で、囲まれたすき間がどれくらい残るかも数えて伝えておけば、決める前に分かった。
