# WS-0001 のふりかえり（2026-10-30）

対象：MWIZ-WS-0001 土台（TASK-0001〜0003、PR #25・#28・#29）

ふりかえりは YWT の形で書く：**Y**＝やったこと、**W**＝わかったこと、**T**＝つぎにやること。

## このふりかえりに出てくる言葉

| 言葉 | 意味 |
| --- | --- |
| WS（ワークストリーム） | 作る作業のまとまり。WS-0001 は「土台」で、アプリを公開し、ホーム画面に追加でき、困ったときに立て直せるようにする部分 |
| TASK | WS の中のひとつひとつの作業。1 つの TASK を 1 つの PR にする |
| PR（プルリクエスト） | 変更を本流（main）に入れてよいか、確かめてもらうための申請。オーナーがマージ（取り込み）すると公開される |
| 枝（ブランチ） | 本流から分けた作業用の写し。作業が終わってマージされたら消す |
| 確認 ID | 「何を確かめるか」1 つごとに付けた番号（例：TC-0005-03）。テストの名前の先頭に付ける |
| 自動テスト | プログラムが自分で画面を動かして結果を確かめるもの。E2E は、本物のブラウザを自動で操作するテスト |
| CI | GitHub が PR のたびに、自動テストやチェックを動かしてくれる仕組み。「CI が緑」は全部通ったという意味 |
| Service Worker | アプリのファイルを端末に保存しておき、通信がなくても開けるようにする、ブラウザの仕組み |
| TD（詳細設計） | プログラムをどう組み立てるかを決めた文書 |

## Y（やったこと）

- 前回の T：最初の WS なのでなし。
- **TASK-0001 開発の土台**：アプリを作る道具をそろえた。書き方のまちがいや、文書どうしの食い違い（番号・版のずれ）を自動で見つけるチェックを作った。GitHub が PR のたびにチェックとテストを動かす仕組み（CI）と、本流に入れたら公開する仕組みも作った。公開 URL は、03 の試作から本物のアプリに切り替わった。
- **TASK-0002 アイコンとインストールの案内**：ホーム画面のアイコン 5 種類を、プログラムで描いて作った（図柄の細かい値は TD-0005 に記録）。タイトル画面に「インストール」の案内を付けた。
- **TASK-0003 更新と立て直し**：
  - 新しい版を公開したら、「更新」の帯が出るようにした。押したときだけ切り替わる。
  - 起動に失敗したら、このアプリが端末に保存したファイルだけを消して、自動で読み込み直すようにした。
  - 「なおす」を押したあとの動きは仕様書になかったので、決めて TD-0005 に書いた。
- 確認 ID 12 個を自動テストにした。CI は 3 回とも、やり直しなしで全部通った。実機（iPhone 11・PC）で公開 URL が開くことを、オーナーに確かめてもらった。

## W（わかったこと）

- **作業計画で、その時点ではまだ書けないテストを 61 個も割り当てていた。**
  - 何が起きたか：最初の作業（土台）に、「戦闘画面で敵の絵を出すまで遊ぶ」テストなどを入れていた。戦闘画面は 11 番目の作業で作るので、最初の作業ではテストを書けない。
  - なぜ起きたか：テストを、ユーザーストーリーの番号で機械的に作業へ振り分けた。そのため、「その作業の時点で、必要な機能がもうあるか」を見ていなかった。
  - どうしたか：最初の作業を始めてから気づいた。322 個すべてを点検して、機能がそろう作業へ移し、計画を直した。
- **マージされたかを確かめずに作業用の枝を消して、PR を 2 つ閉じてしまった。**
  - 何が起きたか：「WS-0001 を始めてください」を、前の 2 つの PR が本流に入った合図だと思い込んだ。実際にはまだ入っていなかった。GitHub は元の枝が消えると PR を自動で閉じる。
  - どうしたか：すぐに枝を元どおりに作り直し、PR を開き直した。中身は失われていない。
- **仕様書で決まっていなかった所は、その作業で決めて設計の文書に書く流れで、うまく進んだ。** アイコンの細かい値と、「なおす」を押したあとの動きがそうだった。
- **起動の失敗をわざと起こすテストで、つまずいた。**
  - 何が起きたか：テストでは、アプリのファイルを読めなくして、わざと起動を失敗させる。ところが、Service Worker が端末に保存したファイルを先に出してしまい、失敗が起きなかった。
  - どうしたか：そのテストでは Service Worker を止めて動かした。
- **作業用のパソコン（Windows の PowerShell）の決まりで、2 か所つまずいた。**
  - コマンドに付けた設定の一部が、うまく届かなかった。届く書き方に替えた。
  - 本流を取り込み直したあと、ファイルの改行の形式が変わった。そのため、文書の中の文字を置き換える処理が一致しなかった。改行の形式に頼らない書き方に替えた。

## T（つぎにやること）

- **作業計画を書いたら、PR の前に「どのテストも、その作業の時点で書けるか」を点検する。** 今回のように、あとから計画を直す手間を防ぐため。→ 手順書 SDD-PROCESS の §8「06 作業計画」に足す。
- **作業用の枝を消すのは、PR がマージされたことを GitHub で確かめたときだけにする。** 次の指示を、マージの合図と思い込まないため。→ 手順書 §1「マージ後の片付け」に足す。
- **ふりかえりには、エンジニアでない人にも分かる解説を付ける。** 最初に言葉の表を置き、「わかったこと」は「何が起きたか・なぜ・どうしたか」で書く（オーナーの依頼、2026-10-30）。→ 手順書 §9「ふりかえり」に足す。
- **アプリのファイルを止めたり差し替えたりするテストでは、Service Worker を止めて動かす。** 保存されたファイルが先に出て、テストが思ったとおりに動かないのを防ぐため。→ 手順書 §8「05 テスト」に足す。
