## W（わかったこと）

- **前のタスクのテストが 1 つ、確認 ID として数えられていなかった。**
  - 何が起きたか：TASK-0009 で書いたテストの名前が「TC-0038-04useSeed で…」と、確認 ID と文がつながっていた。check:docs は確認 ID の後ろに区切りがないと数えないので、テストは毎回動いて通っていたのに、確認 ID がテストにないことになっていた。
  - なぜ起きたか：テストを書き足すとき、編集の道具に渡した文の末尾の空白が落ちた。check:docs は「テストにない確認 ID」を注意として数だけ出すので、1 つ減っても気づかなかった。
  - どうしたか：今回のタスクで「増えるはずの数（121 + 25）」と実際の数（145）が合わないことに気づいた。本流と比べて見つけ、同じように空白が抜けていた 3 つを直した。
- **テストケースの手順が、文の折り返しのせいで成り立たなかった。**
  - 何が起きたか：TC-0011-03 は「戦闘のメッセージが PC で 7 行並ぶ」ことを確かめる手順だった。戦闘の文は長く、どの画面でも 2 行に折り返すので、7 つは並ばない。
  - なぜ起きたか：テストケースを書いたとき、1 つの文が 1 行に収まる前提で考えていた。
  - どうしたか：TC-0011 を v1.1 にし、「並ぶのは最大以下・最新の行が出る・欄の高さを超えない」に直した。行の数をちょうどで確かめるのは、短い文（「かべだ」など）の場面だけにした。
- **作る順の前倒しが、この WS でも 2 つ起きた。**
  - 何が起きたか：勝ったときのドロップ（TASK-0014 の担当）と、ボスを倒したときのクリア（TASK-0012 の担当）を、TASK-0010 で作った。
  - なぜ起きたか：仕様で「勝つと、レベルアップ → ドロップの順に乱数を引く」と決まっていて、勝つ処理と切り離せない。作業計画は、ユーザーストーリーの区切りで TASK を分けていた。
  - どうしたか：TD-0002 に前倒しを書き、確認 ID のテストは予定どおり後の TASK で書くことにした。
- **テストの場面の作り方で、3 か所つまずいた。** どれもアプリの不具合ではなかった。
  - `#` 以降だけが違う URL へ移っても、ページは読み込み直されない。保存を消して開き直すつもりが、前の状態のままだった。いったん空のページ（`about:blank`）へ移ってから開くようにした。
  - プレイ中の状態が残っていると、タイトルや名前入力を開いても、今の場所の画面に移される（仕様どおりの動き）。保存を消してから開くようにした。
  - 見出しのあるウィンドウ（ErrorPanel）は上に余白を取り、ダンジョンの狭い画面では画面に収めるために景色が縮む。「メッセージ欄と同じ位置」は、余白を含めた外側の上の端で、高さに余裕のある画面で比べた。

## T（つぎにやること）

- **TASK の PR の前に、check:docs の「テストのコードに N」が、その TASK の自動の確認 ID の数だけ増えたかを確かめる。** 確認 ID が数えられていなくても、注意の数だけでは気づけないため。→ 手順書 §4.3「07 実装」に足す。
- **テストの名前を書き足すときは、確認 ID のすぐ後ろに空白を入れ、編集の道具に渡す文を空白で終わらせない。** 末尾の空白が落ちて、確認 ID が文とつながるのを防ぐため。→ 手順書 §8「07 実装」に足す。
- **メッセージの行の数をちょうどで確かめるテストは、折り返さない短い文の場面で作る。長い文の場面は「最大以下・最新の行が出る」で確かめる。** 文の長さと画面の幅で、並ぶ行の数が変わるため。→ 手順書 §8「05 テスト」に足す。
- **作業計画で TASK を分けるときは、乱数を引く順が決まっている処理（勝利 → 成長 → ドロップなど）を、同じ TASK に入れる。** 分けると前倒しになり、設計書を何度も直すことになるため。→ 手順書 §8「06 作業計画」に足す（このプロジェクトの残りの TASK は、作業計画どおりに進める）。
- **E2E で保存を消して開き直すときは、いったん `about:blank` へ移ってから開く。** `#` 以降だけが違う URL へは、読み込み直さずに移るため。→ 手順書 §8「05 テスト」に足す。
