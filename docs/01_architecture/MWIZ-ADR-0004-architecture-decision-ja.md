# ADR-0004 画面はブラウザの中の「ゲーム API」を通してだけ状態を変える

## 状況

元の WIZ は「サーバーが正」で、画面は API が返した状態（GameView）とメッセージを表示するだけだった。画面の仕様（応答待ち・二重送信の防止・遷移の保留・エラーの扱い・見せない情報）は、この分け方を前提に書かれている（仕様書 §11）。サーバーをなくしても（ADR-0001）、この分け方を保てば第 1 部の画面の動きをそのまま作れる。

## 決定

ブラウザの中に **ゲーム API**（`src/api/`）を置き、画面はこれを通してだけ状態を変える。

- 操作は元の REST API と 1 対 1（`POST /api/dungeon/move { action }` → `api.move({ action })` など 20 の操作。仕様書 §22.2）。引数・結果の形 `{ state: GameView, messages }`・エラー（`GameError { status, error, message, details? }`、status は元の HTTP ステータスと同じ番号）も同じにする。
- すべての操作は **Promise を返す**（中身は同期で動く）。画面の「応答待ち」「二重送信の防止」は元のまま作る。テスト用に応答を遅らせられる。
- 操作の共通の流れ `run`：保存から読む → ルールで計算 → 書く直前に revision を読み直して書く（違えば 409 `conflict`）→ GameView に変える。CLEARED に入ったら、プレイ中の状態とセーブをまとめて書く（ADR-0006）。
- GameView に見せない情報（未踏破のマスの壁・ボスの位置・敵の HP・revision）を入れない。画面層は GameView とメッセージ以外のゲームの値を持たず、計算しない（例外は仕様書 §11.1）。
- 保存・乱数・時刻は、ゲーム API を作るときに受け取る（本番は localStorage・`MathRandomRng`・今の時刻、テストは偽の保存・`SeededRng`）。

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. 元の API と同じ形のゲーム API（採用）** | 第 1 部の画面・エラー・受け入れ基準をそのまま使える。元の API の統合テストを、DB の代わりに偽の保存でそのまま書ける | 1 人用・端末内なのに、revision やエラーの番号など、元の形のための部品が残る |
| B. 画面からルールの関数を直接呼ぶ | 部品が少ない | 画面がルールの状態（見せない情報を含む）を持つ。第 1 部の書き方と合わなくなる |
| C. 同期の API にする | 書きやすい | 応答待ち・二重送信の防止の作りが仕様書と変わる。テストで遅延を入れられない |

## 結果

- 元の API のテスト（e2e）に当たる確かめは、`tests/api/` の単体テスト（偽の保存）で行う（ADR-0011）。
- 続けられないエラー（status 500：`storage_error`・`internal_error`）は ErrorPanel に出す（仕様書 §11.9）。
